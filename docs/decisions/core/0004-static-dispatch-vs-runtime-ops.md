## 背景（Context）

在传统的嵌入式面向对象（OOP）C 语言开发实践中（如 Linux 内核设备模型、Zephyr 驱动架构以及本工作区的参考基线 `.claude/skills/embedded-best-practice/references/`（原 `chigo-micro/docs/vendor/embedded-best-practice/` 已并入 skill bundle）），为了实现外设驱动的统一抽象与解耦，通常会采用 **“运行期 ops 表多态”** 与 **`container_of` 宏反推子类** 的设计范式。

其典型结构如下：
1. **抽象基类与虚表**：
   ```c
   struct device_ops {
       wink_status_t (*read)(struct device *dev, void *buf, size_t len);
       wink_status_t (*write)(struct device *dev, const void *buf, size_t len);
   };
   struct device {
       const struct device_ops *ops;
       void *private_data;
   };
   ```
2. **运行时调用**：
   `dev->ops->read(dev, buf, len)`
3. **运行时子类转换**（使用 `container_of` 根据 `struct device` 地址推算具体设备结构体地址）。

然而，本项目（Wink-AI / WinkMicroOS）有意识地**偏离了这一业界通用范式**，转而采用 **“编译期静态分发 + 命名式 API + POD 结构体”** 的扁平模式。这引发了架构评审及团队对于“该方案是否真的可行”、“是否违背最佳实践”以及“具体选型考量”的深入探讨。我们需要通过本 ADR 记录其背后的深层技术逻辑与选型决策。

---

## 方案比选（Options）

### 方案 A：经典运行期 ops 查表多态（Linux/Zephyr 范式）

- **优点**：
  1. **高度抽象与规范性**：上层业务层可以通过一套统一的 API（如 `device_read`/`device_write`）访问所有设备，极具扩展性。
  2. **运行时动态绑定**：支持设备运行时热插拔、驱动动态切换（例如在运行过程中根据传感器返回值，将底层实现从 HC-SR04 动态替换为 VL53L0X）。
  3. **集中管理能力**：容易实现全局设备管理器，支持使用链表遍历所有外设进行集中生命周期管理（如统一初始化、统一低功耗挂起）。
- **缺点与痛点**：
  1. **AI 代码生成极不友好（Wink-AI 核心痛点）**：大语言模型（LLM）对复杂 C 指针强转（如 `(struct dal_base_t *)dev`）和 `container_of` 宏的多层嵌套，在代码生成时极易产生语法错误或逻辑幻觉。静态规则也极难对其进行指针安全分析，容易引入野指针等安全隐患。
  2. **WebAssembly 仿真性能与体积恶化（Wink-AI 核心约束）**：在 Wasm 运行环境中，大量的运行时函数指针跳转（`call_indirect`）会破坏 Wasm 的控制流优化，降低运行速度。同时，为支持多态而引入的运行期基础设施会明显增大 Wasm 的体积。
  3. **单片机 RAM 开销**：在资源受限的 MCU 上，每个设备实例都需要在内存中额外维护 4-8 字节的 ops 指针。
  4. **过度设计（Over-engineering）**：Wink-AI 项目中，外设拓扑图在前端低代码编排面板中已经是确定的。通常情况下，一块开发板上绑定的具体传感器型号（如 HC-SR04）在编译期就已经确定，不存在运行时切换驱动型号的刚需。

---

### 方案 B：编译期静态分发 + 命名式 API + POD 结构体（当前采纳方案）

- **优点**：
  1. **极佳的 AI 可生成性与静态校验性**：API 命名直观（如 `dal_ultrasonic_read(&front_radar, &distance)`），LLM 可以 100% 确定性地生成，且静态代码检查工具（Safe Codegen 规则）能以极低成本验证其接口匹配与指针安全性。
  2. **高度契合 Web 仿真（Wasm）特性**：静态分发消除了 `call_indirect` 的运行时开销。更重要的是，基于编译期静态路由（`#ifdef SIMULATION`），可以在仿真环境下**直接 Bypass 旁路物理信号电平的模拟**，直通 Web 3D 渲染器的碰撞距离计算结果，将 Wasm-JS 频繁通信带来的性能开销降低几个数量级。
  3. **简易且零内存开销**：每个外设实例退化为纯 POD 数据结构（如 `dal_ultrasonic_t`），不包含任何函数指针，节省 RAM 空间，且在调试时可以直接在 gdb / 仿真监控中查看到变量的所有真实数据，没有虚表带来的调试迷雾。
  4. **静态设备树契合**：通过低代码面板拖拽生成的物理拓扑，在部署前由代码生成器直接转为 `device_tree.c` 里的静态全局结构体（如 `front_radar`）。静态路由完全满足系统集成。
- **缺点**：
  1. **新增器件的开发开销**：添加一种全新的器件需要独立设计一套独立的 API 和数据结构，无法复用一套统一的 ops 虚表接口，扩展性不如经典范式。
  2. **丧失统一句柄管理能力**：无法将不同外设放入同一个数组或链表进行统一的初始化或遍历。
  3. **限制了热插拔和运行时动态切换**。

---

## 决策结论（Decision）

经过评估，**采纳方案 B（静态分发 + 命名式 API + POD 结构体）**。

### 为什么该方案可行？
1. **静态编排前提**：Wink-AI 系统的应用场景是“低代码图形化编排”。传感器引脚、外设型号在拖拽完成的那一刻（编译期）就已经完全确定，不需要运行时动态查找或热插拔。
2. **设备树静态 Codegen 兜底**：通过自动生成 `device_tree.c` 将配置与 API 进行编译期绑定，完全代替了传统操作系统在运行期的 `MODULE_INIT` 注册和 ops 绑定过程。
3. **特定领域的痛点权衡**：本项目并非通用的微型 RTOS（如 RT-Thread / Zephyr），而是一个**以 LLM 代码生成为核心体验、以 Web 浏览器端高帧率基准仿真为命门**的垂直智能硬件开发平台。**AI 生成的安全可靠性**与**Wasm 仿真性能**是系统设计的 P0 级约束，其优先级远高于“通用驱动框架的运行时扩展性”。

因此，本项目有意识地偏离“运行期 ops 多态”是合理且非常可行的。

---

## 后果与约束（Consequences & Constraints）

1. **命名空间与 SSOT 管控**：由于各外设 API 彼此独立（如 `dal_servo_xxx` 与 `dal_ultrasonic_xxx`），必须建立严格的 Device Registry（外设规范清单），确保代码生成器、仿真器、真机驱动这三者的 API 命名与参数格式完全一致（防范架构评审中指出的 `js_sim_get_ultrasonic_distance` 签名冲突等问题）。
2. **明确运行时热插拔为 Non-goal**：不为极小概率的运行时更换传感器类型需求做架构妥协。
3. **演进与退出路径（Evolution Path）**：
   若未来确实面临“同一种业务抽象（如距离传感器）需要支持多种具体硬件实现（如超声波和激光）运行时并存且切换”的需求，演进策略如下：
   - **不破坏 BAL 层的静态 API 契约**。
   - **在 DAL 内部进行局部多态化**：例如，在 `dal_ultrasonic.c` 内部引入微型的 ops 虚表，仅针对该具体外设进行多态分发；或者根据设备实例中的配置字段（如 `sensor_type`），在 DAL API 实现内使用静态 `switch-case` 分发。
   - 这样既保留了对上层 AI 生成和仿真的静态命名友好性，又在局部获得了运行时多态的灵活性。
