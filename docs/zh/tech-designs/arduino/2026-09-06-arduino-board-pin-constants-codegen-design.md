## 1. 背景与问题 (Problem Statement)

### 1.1 Arduino 引脚常量在上游生态中的位置

未修改的 Arduino Sketch 普遍直接使用引脚符号常量：

```cpp
pinMode(LED_BUILTIN, OUTPUT);
digitalWrite(D2, HIGH);
int v = analogRead(A0);
```

在上游 Arduino 中，这些常量**不是**核心 API（`cores/arduino/`）定义的，而是由**板级支持包变体头**提供：

```text
arduino-avr-core/
├── cores/arduino/                      # 核心 API，不定义任何具体引脚
└── variants/standard/pins_arduino.h    # 板级：#define LED_BUILTIN 13、#define A0 14 ...
```

每支持一块板发布一个 `variants/<board>/pins_arduino.h`，构建时按所选板子选一个变体。引脚常量本质上是**板级事实**，不是框架事实。

### 1.2 wink-micro-os 现状：该供给点为空

对 `wink-micro-os/frameworks/arduino/` 的实测结论（2026-09-06）：

- 框架内**不存在** `variants/` 目录或 `pins_arduino.h`；全框架 grep `LED_BUILTIN` / `#define D#` / `#define A#` 零定义；
- 示例 `arduino_blink_demo.ino` 第 9 行不得不**在 sketch 内手写** `#define LED_BUILTIN 2` 才能编译；
- 运行时侧存在弱符号引脚表 `arduino_pin_map[64]`（`frameworks/arduino/src/Common.cpp`），但内容为硬编码恒等表（`pin N → GPIO N`），注释预留了 "Individual boards (BSPs) can override these symbols" 的覆盖口，**当前无任何 BSP 或 codegen 覆盖它**。

即：今天一份不修改的 Arduino 原生 sketch 写 `pinMode(LED_BUILTIN, OUTPUT)` 会**编译失败**。"Arduino 原生代码零修改"这一平台承诺在引脚常量这一环上存在缺口。

### 1.3 与 C51 模型的根本差异

8051 侧不存在同一问题，因为 Keil C51 语言有原生硬件位类型：

```c
sbit KEY = P3^2;   /* 引脚选择 + 命名 + 句柄三合一，编译期解析为 SFR 位地址 */
```

- SFR 端口地址（P0=0x80 … P3=0xB0）是 **8051 内核架构常量**，由芯片寄存器头（`REGX52.H` 等，经 `wink_mcu.h` 按 `WINK_MCU_*` 宏路由）提供，与具体板卡无关；
- 板级差异（按键接 P3.2 还是 P1.0）写在**用户源码的 `sbit` 声明**里；
- 仿真侧由 `mcs51_proxy.hpp` 以 C++ 代理模拟 SFR，PinArbiter 按 `port*8+bit` 线性通道号注入（见 [MCS-51 零代码侵入设计](../mcs51/2026-08-27-mcs51-zero-code-simulation-and-proxy-design.md)）。

**结论**：C51 的零修改由语言原生机制白捡；Arduino 的零修改必须有人供给整数引脚常量，而这个供给点目前空缺，需要选择补法。

## 2. 候选方案

### 方案 A：手写静态变体头（上游 Arduino 模式）

在框架树内为每块板维护 `frameworks/arduino/variants/<board>/pins_arduino.h`，内容为手抄的 `#define` 常量，构建时按 board 名选择变体目录。

- 优点：与上游 Arduino 概念同构；静态头可读、可 git blame、IDE 可跳转；全部改动在开放的 `wink-micro-os` 树内，不依赖闭源 codegen 引擎排期。
- 缺点：见 §3。

### 方案 B：codegen 从 board.json 生成 `wink_board_pins.h`

codegen 在每个 app 的构建树 `generated/` 下发射 `wink_board_pins.h`，数据直接取自板级 SSOT（`boards/<board>.json` 的 `headers` 与 `onboard_devices`）；`frameworks/arduino/include/Arduino.h` 通过 `__has_include` 守卫自动引入。生成规则契约见 [板级定义规范 §3.5](../../../../wink-tools/tools/codegen/boards/README.md)。

- 优点：见 §3。
- 缺点：emitter 位于闭源交付的 wink-tools 引擎树（本 checkout 中 `wink-tools/` 仅含板级 JSON），交付路径跨仓库。

## 3. 决策：选择方案 B

### 3.1 决定性理由：app 局部自定义板是 A 的结构性盲区

板卡加载器支持三级来源（板级定义规范 §4.2）：

1. **App 局部**：`<app_dir>/boards/*/<board>.json` —— 用户可在微应用内携带 SDK 从未见过的自定义板；
2. `$WINK_AI_EMBEDDED_DIR` SDK 树；
3. 工具链内置默认。

自定义板是平台**设计内的扩展能力**。board.json 一旦放入 app 局部目录，前端画布丝印、走线端点、`$board.headers.X` 解析、PinArbiter 通道**立即全部生效**——这些消费方全部读 JSON。但方案 A 要求框架树中预置 `variants/<board>/pins_arduino.h`，**用户私有板不可能在 wink-micro-os 框架里预置头文件**。结果：自定义板在 UI/仿真全链路可用，唯独"Arduino 原生代码零修改编译"对它永久失效。

A 方案若要补齐该盲区，最终只能在构建期从 board.json 生成头——即退化为 B。因此对 wink 而言不是 A/B 二选一，而是 **B**，或 **A + 早晚仍要做 B**。

### 3.2 两份真理的漂移代价

方案 A 使板级引脚数据存在两份副本（board.json 与变体头）。其影响需如实评估：

- **频率低**：板级定义变化很慢，日常开发几乎无感；
- **故障形态坏**：漂移**不产生编译错误**。board.json 修改后设备树、画布、仿真通道全部用新值，唯独固件常量是旧值——sketch 照常编译，仿真时电平投递到无接线的通道，表现为"传感器无读数/LED 不亮"，排查路径很长；
- **交叉校验测试的悖论**：若写测试比对变体头与 board.json，推导器本身就是 B 的 emitter——测试完成之日，手写头即成为可被生成物替代的冗余副本。

此外真机目标（物理 AVR 上 D0=PD0、A0=ADC6，编号不恒等）将来需要**强定义 `arduino_pin_map[]`** 覆盖恒等弱表，A 方案需手抄第三份数据；B 方案由同一 emitter 顺手生成 `.c`。

### 3.3 与平台既有架构同构

平台早已确立"board.json 为硬件 SSOT、固件 C 常量由 codegen 发射"的模式：

- `wink_config.h`（`WINK_RUNTIME_TICK_MS`、`WINK_MCU_*` 宏）；
- `device_tree.c/h`（设备句柄、实例计数、引脚号——`$board.headers.X` 在 codegen 期解析为整数）；
- `mcs51_board_config.h`（线性引脚↔端口位换算公式宏）。

引脚常量没有理由成为唯一一份脱离 SSOT 的手抄副本。且生成头是**构建配置期产物、编译期静态**：固件视角与手写头完全无差异，零运行时开销。

### 3.4 A 方案的定位：仅作排期受限时的临时止血

若引擎仓库排期阻塞，可先为 5 块内置板手写变体头让 demo 解除 sketch 内 `#define`，但必须：

- 在头文件注释与任务跟踪中注明"过渡方案，codegen emitter 交付后删除"；
- 不做变体选择映射之外的扩展投资，避免临时方案固化为双轨。

## 4. 设计规格（方案 B）

### 4.1 生成产物

每个 app 构建时在 `generated/` 下发射 `wink_board_pins.h`：

```c
/* AUTO-GENERATED by wink-tools codegen from boards/<board>.json. DO NOT EDIT. */
#ifndef WINK_BOARD_PINS_H
#define WINK_BOARD_PINS_H

#ifndef D2
#define D2              (2)
#endif
#ifndef A0
#define A0              (36)
#endif
#ifndef LED_BUILTIN
#define LED_BUILTIN     (2)   /* onboard_devices.status_led.gpio_pin */
#endif

#endif /* WINK_BOARD_PINS_H */
```

### 4.2 生成规则（与 boards/README §3.5 契约一致）

1. **白名单发射**：仅发射 C 标识符安全且符合引脚命名范式的 headers 标签——`^(D|A|GPIO|IO)\d+$`（PDK 家族 `^P[AB]\d+$`）。带点号的 8051/PDK 端口位标签（`P3.2`、`PA.0`）跳过（由原生 SFR 头服务）；`EN`、`VP`、`3V3` 等特殊功能/电源名跳过，避免与上游核心或业务代码符号冲突；
2. **`#ifndef` 守卫**：每个宏包守卫，sketch 内自定义同名常量优先（同值重定义合法）；
3. **`LED_BUILTIN` 从 `onboard_devices` 推导**：取名 `status_led`/`led_builtin` 的 `type: "led"` 板载设备优先，否则取第一个板载 LED 的 `gpio_pin`。现板推导值：esp32_devkitc_v4 → GPIO 2、arduino_uno_r3 → D13，与上游 Arduino 核心约定一致；
4. **职责边界**：该头只承载手写原生源码使用的引脚常量；设备树外设引脚仍走 `$board.headers.<KEY>` → 整数 → `device_tree.c` 的既有链路，两者不重叠。

### 4.3 框架引入方式（已落地）

`frameworks/arduino/include/Arduino.h` 顶部：

```cpp
#if defined(__has_include)
#  if __has_include("wink_board_pins.h")
#    include "wink_board_pins.h"
#  endif
#endif
```

- `generated/` 已在 include path（`device_tree.h` 同目录被引用），无需改 CMake；
- 头文件不存在时静默跳过：框架自包含，旧 codegen / host-only 构建不受影响；
- 不引入 mcs51/pdk 编译路径：C51 的 SDCC/Keil 编译注入 `D2` 式宏只有污染无收益。

### 4.4 未来延伸：运行时引脚翻译表

真机目标上线时，由同一 emitter 生成 `wink_board_pins.c`，强定义 `arduino_pin_map[]`（Arduino 引脚号 → PAL 物理通道）覆盖 `Common.cpp` 的恒等弱表。仿真目标下线性通道号与 GPIO 号恰好恒等（headers 的值即仿真通道），弱表现状正确，无需提前生成。
