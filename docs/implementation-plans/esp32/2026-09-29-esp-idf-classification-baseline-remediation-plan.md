## 二、逐项问题与解决方案

### Q01：能力定义与能力数组缺少统一解释

**问题与依据。** [分类规范][spec] §三 `required_capabilities` 主要要求 ID 存在于 Catalog；§四主要规定单一主层、`owned_paths` 和废弃周期。尚未明确“原子”的判据、能力实现成立的条件，以及直接依赖、传递依赖、条件依赖和未知值的处理。

**执行风险。** 两位执行者可以填写不同粒度的数组而都认为合规；ID 存在只能证明引用合法，不能证明语义正确或回归范围完整；模式变化（如 DMA 轮询、中断模型）时依赖关系容易破损。

**推荐方案。**

1. 在正文增加“能力契约”定义：能力是具有明确适用条件、可观察行为、成功/失败边界、限制和单一主责的可复用契约。原子性不等于一个函数、一个外设名称或一个文件。
2. 规定拆分/合并原则：可独立承诺、验证或演进的行为应考虑拆分；同一行为只因厂商命名或代码文件不同，不应自动产生重复能力。此次仅制定原则，不调整具体能力清单。
3. **推荐数组记录直接需求，Catalog 通过 `depends_on` 声明能力的依赖图谱，由工具生成有效依赖闭包。** 派生闭包保留依赖来源，不允许手工维护第二份完整数组。每个直接需求都应有源码行为或构建需求的依据。
4. **预留条件依赖扩展性与严格解析防线**：数组是集合，无顺序、不重复。虽然首版工具优先解析无条件必需边，但 Catalog 的 `depends_on` 规范设计中需预留条件依赖结构（例如支持 `mandatory: [cap.a]` 与可选模式条件 `conditional: [{ when: { dma: true }, requires: [cap.dma] }]`），避免在引入外设模式（DMA/轮询、中断/协作）时触发 Schema 破损性重构。**同时设立三条解析防御红线**：
   - 遇到当前解析器尚不支持的条件规则语法时，严禁静默忽略，绝不能据此得出“依赖已满足”结论，必须显式阻断并报告解析器不支持；
   - 条件所引用的配置项缺失时按未知（unknown）处理，严禁默认当作 false 进而隐蔽放行；
   - 条件求值必须严格使用 Q03 中已解析的稳定配置实例，并将求值上下文纳入证据指纹，防止预留扩展沦为漏依赖的后门。
5. 未审定不等于零依赖。审计未完成时，空数组只能解释为未知；已审定的空数组必须说明为何确实无受管能力需求。已有 ID 发生语义变化时记录契约修订及影响；破坏性变化按版本治理处理，禁止保持相同身份而静默扩大或收缩承诺。
6. `implemented` 表示实现状态，不能自动证明所有示例、配置和保真要求均已通过。能力实现依据可以复用，示例集成验收仍须独立建立证据。

**修改落点。** 规范新增能力定义与数组解释段落；[Catalog][catalog] 的契约与 `depends_on` 结构设计；[数据源][data] 的需求依据与配置关联；门禁的引用、环路和闭包一致性约束。

**关闭标准。**

- [x] 用抽象关系 `示例 E → 能力 A → 能力 B → 能力 C`，两位审阅者均能得出同一有效依赖集合，并能解释每条边的来源。
- [x] Catalog 的 `depends_on` 结构定义既支持当前无条件闭包计算，又具备表达条件依赖的语法兼容性。
- [x] 遇到解析器不支持的条件依赖语法或缺失配置时，能够正确阻断并报告未知，绝不产生假满足结论。
- [x] 未知引用、循环依赖、重复成员、未审定空数组不会被当成满足需求。
- [x] 可以追溯“源码/构建行为 → 直接能力需求 → 传递依赖 → 对应验收要求”，而不是只看到 ID 列表。

**待评审取舍 D01。** 推荐“直接需求数组 + Catalog 必需/条件依赖图 + 工具计算自动闭包（带未支持语法阻断防线）”；备选为“每个示例手工维护完整依赖集合”。后者初始数据结构简单，但共享能力变化时会产生大面积重复维护，并提高漏回归风险。

### Q02：六类职责与归属决策树没有形成闭合判定

**问题与依据。** [分类规范][spec] §二职责表包含门面层，但决策树没有门面出口；②合并 PAL/DAL，④又包含协议与器件模型，缺少与既有代码分层的明确对应。决策树针对能力，却直接给出示例级 `out_of_scope_product`。

**执行风险。** 同一需求可能因阅读表格或决策树而落到不同位置；固件侧驱动与仿真侧应答模型可能混淆；局部能力限制可能被扩大为整个示例的产品排除。

**推荐方案。**

1. 将六类明确为“实现职责域”，不把 Build、Host Bridge 等误读为一条自上而下的 C 代码调用层级。保留六类的组织价值，同时提供其与 App/BAL/DAL/PAL/Targets 及门面、仿真运行时之间的映射。
2. 对每个职责域说明主责、禁止行为、允许依赖和定位依据。②内部仍区分 PAL 抽象与 DAL 固件驱动；④明确何时指仿真中的控制器/外部器件应答模型。是否同属某个业务协议，不作为二者互相替代的依据。
3. 补齐纯 ABI/参数/句柄/错误码适配的门面出口，消除“跨 MCU 通用”与“通用调度机制”等条件的判定重叠。每个职责域均应有可达出口；多重命中时先拆清契约，仍有分歧则保留待裁决状态。
4. 明确“单一主责”不等于“不能依赖其他职责域”。一条能力链可以跨域，各契约分别归属，组合关系由 Q01 的依赖规则表达。
5. 将“实现归属”与“支持范围”分为两步。能力归属/限制确定后，再对指定配置中的必需能力汇总判定；产品排除必须有独立范围依据，不能由外设名称或单个物理特性直接推出。

**修改落点。** 规范 §二、§五、架构范例；相关现行架构规范的引用与必要回写。此次方案不直接裁决已有具体驱动应搬到哪个目录。

**关闭标准。**

- [x] 六个职责域均能由判定规则到达；主责、代码位置与允许依赖方向能互相核对。
- [x] 对“固件协议执行”和“被模拟设备响应”能明确区分，不会为得到仿真结果而跳过被测固件逻辑。
- [x] 一个能力不满足时，能说明影响哪个配置及哪项承诺，而不会自动排除整个示例。

**待评审取舍 D02。** 推荐保留六类作为职责域，并补既有分层映射；不另建一套取代 App/BAL/DAL/PAL/Targets 的代码层级。若最终改变既有架构边界，先形成 ADR，再安排实现迁移。

### Q03：支持与保真承诺缺少共同的配置定位单位

**问题与依据。** [分类规范][spec] §三同时具有 `baseline`、`soc_matrix`、一组能力数组和一个 `delivery.state`，却没有定义不同配置的需求与证据如何对应。`supported` 与 `Backend: all` 的承诺含义未统一；`fidelity_contract` 也未明确区分需求与已经兑现的保证。

**执行风险。** 一个配置的通过结果被扩大到其他芯片、后端或功能组合；仅因填写保真枚举就形成超出 [UniSim 生产口径][production] 的支持宣称；Wasm 单靶通过被误当作真机已支持。

**推荐方案。**

1. **将“执行配置实例（Execution Configurations）”确立为实体数组（`executions: [...]`）一等公民**。以“示例 + 已解析的执行配置”为需求和验证的共同定位单位。每个配置实例至少明确：配置标识符（`config_id`）、目标芯片（`target_soc`）、执行后端及宿主环境（`backend: wasm_browser | wasm_node | esp32_hardware | host_native`）、运行模式（`profile`）、有效引脚拓扑及输入指纹。**显式区分 Node 与浏览器宿主**，防止在 Node Headless 下跑通就被误认为在浏览器中可用。
2. 一个示例档案只登记实际承诺的有限配置案例集合，不默认展开所有维度的笛卡尔积。不同配置可以复用公共依赖声明，但交付状态与证据必须独立绑定到具体配置。
3. **明确示例根部 `audit` 的覆盖边界**：根部 `audit` 必须显式声明其审定的具体配置案例与需求契约版本（例如记录 `audited_configs: ["wasm_node_standard", "esp32_devkitc_hw"]` 与指纹）。新增配置实例不能仅因父条目已被 `audited` 就自动继承审定结论；未审定的新配置必须保持独立的 `pending_audit`。
4. 将“硬件适用”“平台实现可用”“在此配置已验证”分别解释和展示。`all` 可以作为规划范围的简写，验证时必须展开到明确集合；**Wasm 仿真跑通不等于真机跑通，一个后端的测试通过绝不能覆盖未运行的配置。**
5. 保真声明分别表达“要求什么”“平台能提供什么”“证据证明了什么”。平台上限引用现行 [A~F 定义][axes] 与生产口径；实现可用性和已验证结论尽可能派生，避免三份手工承诺相互漂移。
6. 超出平台上限的要求可以作为需求记录，但只能得到未满足/阻断结论，不能成为已提供的保证。配置与拓扑信息引用既有 manifest、生成资产及其指纹；明确需求描述与实际解析结果的区别，避免再维护一份独立引脚事实。

**修改落点。** 规范中配置、芯片矩阵、保真契约和示例汇总段落；数据结构中多配置实例与证据的关联；SOP 的配置选择步骤。

**关闭标准。**

- [x] 同一示例在两个不同后端（如 Wasm 仿真 vs ESP32 物理硬件）、不同宿主（Node.js vs 浏览器）的验证结果独立表达；只验证其中一个时，另一个绝不显示已验证。
- [x] 审计结论显式绑定已审配置列表，未审定的新增配置不自动继承父条目的 `audited` 状态。
- [x] 改变有效配置或拓扑后，旧证据不会自动继续证明新配置。
- [x] 每个保真保证都能链接到平台支持依据及对应证据；需求超过上限时有明确未满足结论。

**待评审取舍 D03。** 推荐“一个示例档案 + 多配置实例实体数组（`executions: [...]`）”，明确宿主环境与审计覆盖对象，保持示例 ID 稳定；不为每个配置复制整份示例，也不使用脱离配置的全局泛化 verified。

### Q04：范围、审计、能力可用性和交付状态混用

**问题与依据。** [分类规范][spec] §五的五态混合审计进度、产品范围、投入安排与技术阻断，完成交付后缺少自然的范围内正常状态。[生成器][renderer] 将 deferred 与产品排除都映射为 `[-]`，而 [看板][checklist] 将该符号解释为 Out-of-Scope。当前 [数据源][data] 条目 1（`esp.get_started.blink`）出现严重自相矛盾：`delivery.state` 为 `"verified"`，而 `scope_and_maturity.status` 却仍被标记为 `"in_scope_deficit"`（规划缺口）。

**执行风险。** 已完成条目仍被称为缺口；暂缓被看成排除；输入已变、尚未重验与真正测试失败混为一谈；统计口径失去可信度。

**推荐方案。**

建立**五维正交状态模型**，彻底解耦范围、审计、投入、实现与交付，并保留显式“未知（unknown）”状态：

| 维度 | 回答的问题 | 建议字段与枚举 | 建议维护方式 |
|---|---|---|---|
| **产品范围 (Scope)** | 是否承诺纳入产品目标，排除依据是什么 | `scope.inclusion`: `unknown \| in_scope \| out_of_scope`<br>`scope.exclusion_reason`: 文本/枚举 | 架构审定后登记；**显式保留 unknown**，严禁未审先排 |
| **投入安排 (Schedule)** | 范围内特性是立即投入还是暂缓 | `scope.schedule`: `active \| deferred` | 排期决策，不改变产品范围 |
| **审计状态 (Audit)** | 当前需求与分类结论是否审定且仍有效 | `audit.verdict`: `pending \| audited \| needs_review`<br>`audit.audited_configs`: 已审配置数组 | 架构师/工具审定，绑定已审配置列表与时间戳 |
| **能力成熟度 (Maturity)** | 底层依赖是否满足此配置需求 | 由 Catalog 依赖图与配置自动派生：`unknown \| satisfied \| blocked` | 不在示例中手工维护状态，由工具计算闭包判定 |
| **交付证据 (Delivery)** | 指定配置下是否有真实成功的执行证据 | `executions[].delivery_state`: `planned \| building \| verified \| stale \| regressed` | 执行工具链生成，强绑定防伪哈希与执行报告索引 |

**建议的落地 Schema 结构草案（消除 `blink` 的自相矛盾，遵循教学数据边界）：**

1. **统一绿色勾选 `[x]` 与门禁放行的唯一判据（六位一体闭环）**：
   门禁系统与看板渲染遵循**完全同一套判据**，只有在同时满足以下全部条件时，看板才允许打勾 `[x]`，CI 才判定通过：
   - ① **产品范围**：`scope.inclusion == "in_scope"`（`out_of_scope` 排除项即使拒绝断言通过，也仅显示 `[-] 排除已验证`，绝不打勾）；
   - ② **需求审计**：`audit.verdict == "audited"` 且已审范围显式包含当前配置案例；
   - ③ **依赖闭包**：对应配置的必需能力依赖全部计算为 `satisfied`（无 `unknown` 或 `blocked`）；
   - ④ **交付状态**：该配置在结构化档案中被声明为 `delivery_state == "verified"`；
   - ⑤ **防伪哈希**：绑定的 `assets_sha256`、`scenario_sha256` 与执行记录哈希非空，且与当前代码工作区产物一致；
   - ⑥ **执行结果**：绑定的最新执行报告记录证明**当前配置真实执行成功**（进程退出码 0、正负向断言全部通过、无未捕获异常）。
   *若任何一项不满足（例如即使产物哈希存在但测试断言失败处于 `regressed`、报告缺失或依赖处于 `unknown`），门禁坚决拦截，看板严禁渲染 `[x]`。*
2. **区分失效原因**：需求或契约语义变化触发 `audit.verdict -> needs_review`；相关实现/资产/场景变化导致证据 `delivery_state -> stale`；实际重跑断言失败才是 `regressed`。无关改动不触发全量失效。
3. **历史数据迁移**：旧 `deficit` 迁移为 `in_scope` + `active`；旧 `deferred` 迁移为 `in_scope` + `deferred`；旧 `contract_blocked` 暂存待裁决，不擅自推断产品排除；当前 10 个哈希为 null 的条目因证据不完备，进入历史欠账隔离区，不可继续认定为有效 verified。
4. **统计口径逐维独立**：看板分别统计“范围覆盖率”、“需求审定率”、“交付验证率”，严禁将正交维度混为一谈。

**修改落点。** 规范 §五及交付状态定义；数据迁移规则；生成器、看板图例及统计；Gate 1 的组合约束。

**关闭标准。**

- [x] “范围内且已完成”“范围内暂缓”“尚待审定”“已排除且拒绝测试通过”均能无歧义表达，消灭“已验证却仍是缺口”的语义矛盾。
- [x] 门禁与看板严格遵循统一的六位一体“有效 verified”判据，测试断言失败或依赖未知的配置绝不会被打上 `[x]`。
- [x] 输入变化未重跑（stale）与重跑失败（regressed）显示不同状态；看板与数据源逐维一致。
- [x] 规范中的 Schema 结构示意明确标注为草案且状态为 planned，避免成为占位假凭据的复制源头。

### Q05：verified 尚未绑定当前配置的一次真实成功执行

**问题与依据。** [分类规范][spec] §七 Gate 1 校验审计、资产哈希和场景存在，尚不足以证明“这些产物在这个配置下执行这些场景且通过”。更为严峻的是，当前 [数据源][data] 中宣称的 10 个 `delivery.state == "verified"` 条目，其 `assets_sha256`、`scenario_sha256`、`last_verified_at` 和 `last_verified_commit` **全部为 `null`**！结构化执行凭证完全缺失，不可继续认定为有效 verified。同一套 Wasm 三件套要求也无法自然表达 host-native、构建验证、预期拒绝验证，以及同源双靶（Wasm vs ESP32 物理真机）的差分检验。

**执行风险。** 凭证缺失的条目占据“已完成”统计；旧报告配新产物、场景存在但没执行、结果来自其他配置，仍可能形成表面完整的交付档案；仿真跑绿但真机跑挂的同源漂移无法被拦截；或过度承诺导致虚实恒等的虚假宣称。

**推荐方案。**

1. **强绑定可复核的执行证据记录**：执行证据记录至少绑定：示例/配置 ID、有效能力契约集合指纹、相关源码/构建输入版本、工具链与执行器版本、产物清单及哈希、场景哈希、执行结果、断言结果与时间信息。**严禁哈希为 `null` 的记录成为 `verified`**。记录由真实执行链路生成，清单引用记录并校验绑定关系。
2. 分开“结构有效”“语义合规”“执行成功”三类检查。verified 必须同时成立；有文件、有哈希或进程退出码为零，均不能代替承诺所需断言通过。
3. 建立“契约要求 → 验收断言/共享契约测试 → 执行结果”的覆盖关系。共享底层测试可以复用，但必须证明适用于当前实现和配置，并保留示例集成行为验收；负向测试要能识别相关假成功行为（如永远返回成功的假空桩），不能只计数。
4. 按下表定义证据类型，具体验收内容仍由示例声明的行为契约决定：

| 验收类型 | 必须证明的内容 | 成功结果的含义 |
|---|---|---|
| **Wasm 运行验证** | 对应资产、有效配置、实际场景执行与正负向断言 | 此 Wasm 配置满足声明的行为契约 |
| **Host-native 运行验证** | 对应本机产物、运行环境/配置及实际测试结果 | 此 Host 配置满足声明的行为契约，不自然扩大到浏览器 |
| **构建工具链验证** | 指定构建输入及构建/链接/产物断言；契约要求运行时再附运行结果 | 指定构建语义成立，不因构建成功而宣称完整运行时支持 |
| **预期拒绝验证** | 指定配置在规定阶段以规定原因被拒绝；物理排除遵循现行编译期阻断要求 | 拒绝边界成立，不等于示例已支持；任意编译错误不能算成功 |
| **同源双靶差分验证**<br>*(Differential Parity)* | 在绑定的真机与仿真运行记录、指定激励和比较规则下，已观测行为满足声明的等价关系或容差；未覆盖维度不作等价承诺 | 已覆盖维度的观测行为符合预言；遵循 [UniSim 生产口径][production]，严禁承诺全维度虚实恒等 |

5. **差分证据规范与适用范围收窄**：
   - 差分证据必须显式关联两侧真实运行记录（`sim_run_id` 与 `hw_run_id`）、比较规则版本和观测项清单；
   - 时间容差（`tolerance_us`）与数值/状态容差分别独立定义；
   - 仅在涉及关键外设驱动和底层总线协议时要求差分验证，明确哪些交付必须做差分，**严禁将物理真机差分变成所有普通 Wasm 示例验证的隐含阻塞前置**。
6. 证据必须有有效性规则：相关输入变化后标记待重验，保留历史记录；不得仅替换清单中的哈希就使旧成功结果重新有效。

**修改落点。** 规范新增交付证据段落；Playbook 的验收流程；数据中的证据引用；Gate 1 与 Gate 4 的证据有效性规则。证据格式设计不要求更换现有测试执行器。

**关闭标准。**

- [x] 现存 10 项空哈希条目移入隔离区，没有任何哈希为 null 的配置能被认定为有效 verified。
- [x] 双靶差分承诺明确限定在已观测项与容差范围内，未覆盖维度不作恒等承诺，不违背生产口径。
- [x] 正常运行、构建、预期拒绝和同源双靶差分可以使用不同证据类型，并有清晰结果标签。
- [x] 任何一个 verified 配置都能定位实际执行报告并复核其输入、断言和结果。

**待评审取舍 D04。** 推荐保留既有执行器，统一其证据契约（含双靶差分观测边界）与结果归一规则；不强迫所有验收类型产出相同 Wasm 文件。

### Q06：事实所有权、规则优先关系和生效过程尚未统一

**问题与依据。** [分类规范][spec] 铁律四禁止手工改看板，[Playbook][playbook] §六却要求改 Markdown 与统计。更突出的是，规范开篇宣称 `.gates/gates.yaml` 和 `python .gates/run_gates.py` 为当前唯一门禁 SSOT，但**工作区内根本不存在 `.gates/` 目录**。规范是 Proposed，门禁技术设计是 Accepted/待实施，[实施计划][gate-plan]仍为待执行，把“未来规划”当成“当前强制”，造成严重的法理与工程断层。

**执行风险。** 开发者遵循不同文档会得到不同写入路径与准入结论；已接受设计被误解为已经启用；迁移期豁免演变为永久宽松规则。

**推荐方案。**

1. 在规范开篇增加事实所有权与消费关系表：全局规则由规范定义；能力契约正文由 Catalog 持有；示例需求和审定记录由结构化档案持有；实际配置/拓扑通过既有 manifest 与生成资产定位；执行报告提供运行证据；看板只派生展示。
2. 规范引用现行架构 SSOT 的产品边界，不另外扩大承诺。门禁注册表负责规则实现、触发与严重度配置，但不得在未登记例外时降低规范的不变量。增加“规范条款 → 数据约束 → Gate 规则 → SOP 步骤 → 看板含义”的追踪表。
3. Playbook 增加“选择配置并完成需求审定”的入口步骤，交付阶段统一为“记录证据并更新结构化数据 → 校验 → 生成看板”。Catalog 状态表和范例中的事实优先生成或引用，避免独立维护副本。
4. **制定清晰的门禁工具链两步走切换路线**：
   - **步骤一（当前过渡期）**：立即修正规范开篇描述，如实标注 `.gates/` 为*实施中架构*（引用 [gate-plan][gate-plan]），当前以现有校验脚本（如 `generate_checklist_v1_1.py` 等）为过渡期操作入口，去除“已全面生效”的虚假描述；
   - **步骤二（正式落地）**：待集中式门禁框架代码就绪后，先以过渡模式（`--mode pr --allow-legacy-debt`）挂载，验证无误后再切换为全量硬阻断。
5. **建立历史存量债务隔离区（Legacy Debt Quarantine）与 TTL 规则（坚持门禁只读不写文件）**：
   - 新增或变更 verified 声明，相关证据检查必须为 error；
   - 现存 10 个哈希为 null 的条目进入独立的隔离区白名单配置（如 `.gates/quarantine.yaml`），标记为 `provisional_unverified` 豁免项。**看板对应行渲染为 `[?] 待补凭证`，严禁渲染为绿色勾选框 `[x]`**；
   - **门禁纯函数原则与 TTL 到期处理**：遵循 [门禁技术设计][gate-design] 纯函数约束，**门禁在 CI 运行时严禁修改任何数据文件**。为隔离区条目设定硬性过期时间（TTL，如 14 天/1 个迭代周期）。TTL 到期后豁免立即失效，门禁判为阻断 Error；状态回退（如改为 planned）必须通过独立、可审阅的数据迁移 PR 完成，并记录历史追踪，严禁门禁静默篡改数据；
   - **例外限域**：`--allow-legacy-debt` 仅放行已在隔离区明确登记的“条目 + 配置 + 规则”白名单例外，严禁成为全局宽泛绕过开关。
6. 区分规范版本、数据格式版本与能力契约修订，明确兼容、迁移和复审规则。若采纳的方案改变 Schema/决策树语义，按现行破坏性变更流程确定版本，不预先把它当作普通 v1.2 小修。
7. 保留 [ADR-0090][adr90] 的集中式门禁架构。若需调整其已采纳的严重度安排或其他既定约束，以新的补充/替代 ADR 记录；Accepted ADR 和归档评审不直接改写。决策采纳后同步回写现行规范与配套设计。

**修改落点。** 规范开篇、治理与版本演进章节；Playbook；门禁技术设计/实施计划及必要的新 ADR；事实与规则追踪表；隔离区白名单。

**关闭标准。**

- [x] 按规范或按 SOP 操作，均得到同一事实写入位置、状态和准入结果。
- [x] 规范开篇诚实反映门禁落地现状，不再宣称尚未落地的脚本为唯一已生效 CI 入口。
- [x] 现存 10 项空哈希条目进入隔离区，看板渲染为 `[?]`，设立了明确的 TTL 退出期限；TTL 到期后门禁仅阻断而不直接写文件。
- [x] 新 verified 不因 PR 模式而绕过证据要求；历史例外不能静默扩大或无限延期。

**待评审取舍 D05。** 推荐“新声明严格阻断，历史欠账通过隔离区与 TTL 白名单限域过渡，看板显式标为 `[?]`，门禁只读判定不写文件”；备选是立即要求全部存量满足新规则。前者更符合现实工程节奏，且有明确防腐机制。

### Q07：影响分析与回归策略尚未形成完整闭环

**问题与依据。** [分类规范][spec] §七称为影响闭包，但主要规定直接能力匹配；[门禁技术设计][gate-design] §十也是路径到能力、能力到示例的一层匹配，并可按数量推迟到 Nightly。尚未说明语义/配置变更、未登记路径、延后验证期间状态，以及不同验收类型的分流。

**执行风险。** 间接依赖漏跑；只改 Catalog 的语义却不触发重验；影响越大越可能在 PR 中没有足够验证；不可运行的条目被错误算作全量通过。

**推荐方案。**

1. 复用 Q01 的能力依赖图：变化路径/能力契约 → 受影响能力 → 反向传递依赖 → 受影响示例配置 → 对应验收集合。依赖删改、路径删除/重命名时同时考虑变更前后关系，避免只看新图而遗漏旧消费者。
2. 将能力契约、依赖关系、有效配置、拓扑、场景与验证规则的变化列入触发来源；不仅监听实现源码。影响集合以稳定示例/配置 ID 表达，显示序号只用于展示。
3. 对受管运行时、构建或配置路径出现无法归属的变化，按影响范围保守扩大回归或明确阻断要求补映射；不允许把“无法计算”当作“无影响”。普通无关文档变更不触发全量失效。
4. PR 中必须验证本次新增/更新的 verified 声明，以及受影响核心机制的约定最小回归集。其余广泛回归若移交 Nightly，必须有明确待验证清单；对应旧证据标为过期/待重验，不继续作为当前版本已验证的证明。
5. Nightly 依据验收类型执行正常运行、构建、预期拒绝等集合。尚未审定或无法运行的条目进入明确的未执行报告，不算通过，也不能因其占据清单就声称完成全量运行验证。
6. 定义回归结果处置：成功更新当前证据，失败进入 regressed，基础设施失败保留未完成验证状态；指定责任与关闭条件。资源阈值只能调整调度策略，不能取消最低准入检查。

**修改落点。** 规范 Gate 4；门禁技术设计的影响算法及 PR/Nightly 规则；证据失效与看板聚合规则；Catalog 的路径和依赖关系。

**关闭标准。**

- [x] Q01 的抽象依赖链中只修改能力 C，也能定位示例 E；删除依赖或文件后仍检查原消费者。
- [x] 仅改契约、配置或场景也能触发正确的复审/重验；无法归属时不会输出假空影响集。
- [x] PR 延后回归后可以列出欠验证配置；Nightly 汇总区分通过、失败和未执行，预期拒绝不计入支持率。

**待评审取舍 D06。** 推荐“PR 最小必验集 + 有状态的 Nightly 扩展回归”；具体必验集合与预算在技术设计中确定，不用单一数量阈值直接替代准入标准。

### Q08：正文顺序与规范范例不足以支撑一致执行

**问题与依据。** [分类规范][spec] 第三章先展示大段 Schema，第四章才介绍能力字典；第六章将六个局部展示段落称为完全符合 Schema，但未提供贯通需求、能力、配置、证据与看板的完整可校验档案。

**执行风险。** 读者依赖字段名称猜语义；局部示意被当作合规模板；历史案例、当前事实和强制规则互相混淆。

**推荐方案。**

1. 按下节建议目录重排，以概念、判定、证据和流转规则为正文主线。保留已有有价值的内容，不以篇幅扩张作为目标。
2. 将历史偏差复盘作为附录，并标明其历史基线；具体能力状态表从 Catalog 生成或链接，不成为第二份事实源。
3. 增加至少一个完整端到端规范范例：源码/构建依据 → 明确配置 → 直接能力与闭包 → 主责裁定 → 范围/保真结论 → 正负向验收 → 实际证据 → 数据回写 → 看板结果。
4. 对现有其他打样明确标注“局部示意，不是完整档案”。新增边界范例说明未知依赖、配置未验证和预期拒绝的正确处理；教学数据不能登记为真实 audited/verified。
5. 长 JSON 结构移到附录或独立约束定义，并标明其规范性。保留 Python 插件门禁的现有决策，明确结构约束和跨文件语义约束分别由谁执行，不借本次整理擅自更换门禁架构。

**修改落点。** 规范整体目录、Schema、历史复盘、Catalog 概览、范例章节；配套可校验范例及其生成/验证约定。

**关闭标准。**

- [x] 新执行者能够沿正文顺序完成一条示例配置的判定与交付，不需要从范例猜缺失规则。
- [x] 完整范例能通过与真实档案相同的约束；局部示意和教学数据不会被误认成已验证事实。
- [x] Catalog、数据档案和看板之间没有独立维护的状态副本。
