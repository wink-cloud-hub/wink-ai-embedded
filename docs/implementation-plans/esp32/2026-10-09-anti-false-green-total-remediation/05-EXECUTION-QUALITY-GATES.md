## 1. Phase 0：开始实现前冻结什么

## 2. 每个任务的执行卡与完成条件

任务卡至少有以下字段，实际值在开始任务前填写：

| 字段 | 要求 |
|---|---|
| 身份与责任 | task_id、issue_ids、实现责任人、复核责任人；二者职责可核验，不代填签署 |
| 范围与依赖 | 修改文件白名单、执行配置、必需前置任务、基线与技术设计版本 |
| 验收设计 | 所验证的行为、check/claim/assertion ID、正确对照、有效非等价缺陷、可接受的结果与 deadline |
| 执行与证据 | 实际命令/退出码、运行和工具身份、输入/产物摘要、原始结果引用及摘要、清理与恢复、剩余缺口 |
| 完成复核 | 适用门禁逐规则结果、补丁/提交身份、独立复核决定及覆盖范围、阶段出口回执 |

任务工程状态仅用于计划追踪：待执行 → 执行中 → 已实现待验证 → 已验证待复核 → 完成。代码存在或单测通过只支持相应中间状态，不能直接标完成。该追踪状态不进入 checklist 的 delivery_state。

涉及接受策略、硬件时序、状态、存储或隔离的任务必须满足：

```text
TaskDone =
  实现与当前基线绑定
  AND 必需检查集合完整
  AND 正确对照通过
  AND 指定缺陷被目标检查检出
  AND 适用清理/恢复通过
  AND 独立复核与本轮证据绑定
```

文档索引、链接等低影响任务只执行适当静态校验，不为形式上的“红绿”制造无意义变异。有效非等价变异、自然故障复现或保留的真实失败基线均可承担缺陷敏感性证明；不能要求同一缺陷在已修源码上仍出现。

## 3. 证据分层与七类业务检查

| 层级 | 能证明 | 不能据此扩大声明 |
|---|---|---|
| 合成输入 / Unit | 解析、算法、错误分类、边界 | 固件构建或真实业务经过驱动 |
| 实际 C / OS 集成 | 指定驱动、存储或进程/事务行为 | 未运行的场景或另一个目标 |
| 真实构建与加载 | 实际输入产生指定产物，runner 加载该摘要 | 核心业务正确、真实硬件行为一致 |
| 配置级仿真闭环 | 本轮场景与原始观察下的指定业务、故障和恢复 | 另一个 backend、profile、SoC 或完整物理保真 |
| 审计与正式晋升 | 当前配置满足完整前置条件并读回一致 | 后续变更后的凭据仍有效 |

每个应用 ProofPlan 按现行契约明确 `baseline`、`matcher_self_check`、`env_sensitivity`、`firmware_dependency`、`implementation_mutation`、`fault_handling` 与 `recovery` 的适用检查及完整集合。物理背压、因果穿越、符号/链接/运行见证是相应 Claim 的具体证据，不通过堆积辅助电源断言代替。

N/A 必须说明所依据的既有规则、业务适用性、覆盖配置与有效独立裁定；不得默认免除必需业务变异。纯构建、纯计算、稳态输出等依各自契约设计，不强加无关物理断线、动态迁移或响应包。故障处理允许业务规定的 Fail-Loud 或受控终止，恢复按声明冷启动/复位和持久化策略核验。

每条正式结果至少绑定：执行实体、run_id/attempt、冻结 ProofPlan 与场景摘要、实际构建/加载摘要、runner/规则版本、Claim/Check/Assertion ID、原始观察及其文件引用/摘要、预期极性、实际判定和适用清理。这些字段从真实执行采集，不能用 `has_business_assertion=true`、固定工具版本或 hash(config_id) 代替事实。

## 4. 变异与故障的分类边界

本表是结果分类要求，具体序列化枚举由技术设计冻结；不新增交付状态。

| 情况 | 判定要求 | 晋升影响 |
|---|---|---|
| 原始正确业务 | 所有必需正常检查完整通过 | 仅完成正向部分 |
| matcher 改错预期后失败 | 断言器自检有效 | 不计实现变异击杀 |
| 生效的非等价实现变异 | 相同 fixture/预期下，指定原业务断言在 deadline 内失败；报告能归因至该缺陷 | 记录有效击杀 |
| 指定业务断言仍通过 | 记录变异存活；不得修改预期掩盖 | 阻断，或按既有等价变异独立裁定协议处理 |
| 补丁零匹配、多义匹配或无行为变化 | 记录无效/未生效变异及原因 | 不计击杀，必需检查未完成 |
| 变异源码编译/链接失败 | 保存编译诊断 | 不计击杀 |
| runner 故障、无关崩溃、宿主 deadline 或日志缺失 | 基础设施失败/不完整；与业务内超时断言分开 | 不计击杀或故障处理通过 |
| 外部故障与背压 | 扰动已生效，指定故障处理/溢出断言按契约通过 | 故障类证据有效，不替代实现变异 |
| 扰动撤销与恢复 | 易失状态按复位契约恢复；持久化按声明保留或重建；原基线通过 | 恢复类证据有效 |
| 等价变异豁免 | 核验独立身份、规则、配置、算子、补丁、产物与有效期绑定 | 仅豁免该变异，不免除其他检查 |

L2 预算遵循现行 AFG 契约“每 Claim 最多 1 个”。应用级默认 2 个是资源调度预算，必需集合超过时应在同一冻结基线下拆分运行/调整已确认预算；不能删 Claim、只测前两项或把预算耗尽标完成。

## 5. 阶段出口必须由检查集合推导

QG-0～QG-4 的出口要求分别见各阶段。统一规则如下：

- 执行前冻结 `expected_config_set`、`required_check_ids` 和 `required_rule_ids`；实际结果按身份去重对账。`expected_config_set` 是相应批次必须实际运行的集合；另对治理全集逐项记录已交付、未完成或合法暂缓。缺失、重复、额外或借用结果显式诊断。
- 每项 mandatory 结果必须真实执行且符合预定极性。SKIP、missing、pending、infrastructure failure 和 budget exhausted 不计通过；适用性排除记录依据，不能事后豁免失败。
- 同一坏样本在候选、正式核验、Inspector、晋升和兼容写入入口必须一致拒绝；正确样本必须通过。不能用“全部拒绝”满足反例测试。
- 先核验原始执行结果，再形成引擎资格回执；密封、审计和晋升分别核验各自前置条件。ELIGIBLE 不自动等于正式 verified。
- 任意公开验收入口不得把无参数、空选或未完成执行返回为验收成功；合法 list/status 查询使用独立口径。
- 实现阶段用拔除目标防线/注入已知缺陷的受控反例验证门禁敏感性。代码覆盖率和测试数量仅作辅助指标。

**出口判定器、检查 Schema 与接受入口集成均是实施任务。** 未完成机器强制执行前，阶段必须保留逐项可复核记录并标明工具缺口；正式晋升与全量推广不得越过其强制设施缺口。

## 7. 回执、门禁与发布边界

以下为拟运行目录结构，具体字段与 Schema 复用/扩展在 T0.2 冻结。试验失败也保存原始回执，不写 verified，不覆盖旧包。

```text
.governance/runs/<run_id>/
  baseline / config-set / task-index
  attempts/<app_id>/<config_id>/<attempt_id>/
    source-diff / resolved-proofplan / build-manifest / run-manifest
    reports / logs / probes / mutation-patch / check-results

```

密封前完成日志 flush 与报告收集；payload 文件列表完整绑定路径和实际字节摘要，二进制不做文本归一化。摘要规范、JSON 规范化和 envelope 范围遵循冻结技术设计，避免摘要自引用。审计与衍生回执绑定 payload，密封后不再修改其内容。归档、清单引用切换、读回和恢复均须实际验证。

终验从仓库根目录使用已核验的 CLI。以下命令展示现有入口，变量由任务卡填写；必须先修复相应核验缺口，命令退出 0 不能单独代表质量出口：

```powershell
python -X utf8 -B wink-micro-app/vendor/esp_idfv61/.governance/gates/run_gates.py --mode pr --changed-files $ChangedFilesPath --output-json $GateReportPath
```

Changed-files 必须对应冻结基准与本轮完整改动，包含适用新增文件；不得伪造触发文件。由注册表与变更推导必需 Gate 1～5 规则，核对逐规则执行及实际下游回归结果。nightly 和 require-executed 只能补充运行约束，不能代替集合对账。所需 SDK、winkcli、模型/插件或规则不可用时保留缺口，不使用 no-fail 或放宽 Matcher。纯计划文档编辑只做适用的文档静态校验；实现阶段才执行上述代码门禁。

## 8. 停止、恢复与阶段复核

发现共享资源污染、配置/产物身份错配、未知有效性或必需门禁遗漏时，停止受影响 attempt 和领域推广，保存诊断；其他明确独立领域可继续准备工作。停止后的结果不得标成功。恢复要有问题解决证据、新 attempt 和输入/版本再核验，不清空冻结注册表“重新开始”。

阶段复核包包含：任务与问题矩阵、必需/实际检查差异、真实正确/错误样本回执、补丁与版本、清理/恢复、未完成项及影响配置。复核者可从原始结果重算汇总，并能选择代表配置重放；实际正式发布仍需现行独立审计与对应授权。历史评审只读，新增复验报告记录纠偏和限制。

只有机器出口判据、原始回执和复核决定都与冻结范围一致，才能更新本阶段完成状态。完整裁决但有必需实现缺口可作为阶段进度产物，不能称整改或运行交付全部完成。
