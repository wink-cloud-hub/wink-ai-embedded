## 结论与适用范围

v2.1 已为上一轮主要问题安排隔离、逐 claim 证据、实际身份、发布事务、精确批次与迁移验收，架构主线可以支持开展 L0 技术契约冻结。本轮剩余问题集中于新增措施的适用条件及验收可操作性，无须再扩大为一轮整体重写。

Standards 轴有 3 项，Spec 轴有 5 项；Fast Relink 的同一约束在两轴均被发现，分别保留其实现风险与需求风险。P1 项应在对应契约冻结前解决；P2 项应在相关工作包及 L6 验收前形成明确规则。本记录评审的是计划充分性，不代表这些失败已被运行复现，也不代表 Loop 加固已实施。

## Standards：工程规范与实现可行性

### LS21-01 [P1] Windows 进程清理需要在启动时建立归属与有界回收

**位置：**计划第 201 行（L1-T6），以及第 80、368、443 行。

计划已要求 attempt 归属、整树清理和文件锁退避；但将事后 `taskkill /F /T` 或递归 `psutil` 写成“彻底清除”的充分措施，未说明父进程提前退出、调度器崩溃及输出管道仍被后代持有时的实现方式。

当前 [agent.py:149](../../../wink-micro-app/vendor/esp_idfv61/.governance/tools/loop/agent.py#L149) 与 [pipeline.py:85](../../../wink-micro-app/vendor/esp_idfv61/.governance/tools/loop/pipeline.py#L85) 使用 `subprocess.run(..., capture_output=True, timeout=...)`。本机 Python 标准库的 Windows 超时分支先终止直接子进程，随后调用无 timeout 的 `communicate()` 收集输出。若后代仍持有管道，存在外层超时处理迟迟无法取得控制权的路径；仅在外层捕获异常后执行清理不足以覆盖它。此为源码推导，未运行挂起实验。

建议在进程启动时建立 attempt 级 containment：采用 Job Object 或等价监督机制，处理加入归属前的派生竞争、breakaway、句柄继承和清理超时；维护进程句柄/创建身份，避免仅按可复用 PID 判断归属。调度器异常退出后也应能触发回收，且只清理本 attempt 的资源。`taskkill` 可以作为兜底，不能代替持续归属约束。

Microsoft 文档说明 Job 中的子进程默认继承归属，同时列出 breakaway 例外；`KILL_ON_JOB_CLOSE` 在最后一个 Job 句柄关闭时终止所属进程。因此实施时必须明确句柄所有权，不能只选择 API 名称。[Job Objects 官方说明](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

**验收补强：**组合 AT-18/29，覆盖父进程先退出、后代继承 stdout/stderr、调度器被终止、清理期间继续派生。回收与管道关闭均须有期限；不能以一次 `taskkill` 返回成功代替资源清理证明。文件占用重试应有限，预算耗尽后保留失败并阻断发布。

### LS21-02 [P1] Step-Tick 需要接入已有单一时钟推进契约

**位置：**计划第 108、199 行；涉及第 94、165、367、446 行。

现行 [一致性规范第 95–105 行](../../zh/design/04-wasm-simulation/04-assurance/01-consistency-spec.md#L95) 已规定唯一虚拟时钟、单 Gate 和 HEADLESS 内部快进。[pal_osal_wasm.c:575](../../../wink-micro-os/osal/wasm/pal_osal_wasm.c#L575) 已在任务均等待时推进到下一任务唤醒点。新增“事件轮/Step-Tick”若另建推进者，存在双重推进或跨过场景输入、器件事件与观察截止点的风险。

建议明确复用现有 Gate，并定义全局下一截止点的仲裁：任务唤醒、适用器件事件、场景注入及观察窗口均参与；冻结同刻事件顺序、步长/量化误差、C/JS yield 与异步完成边界。外部仿真能力变更应通过公开 ABI/运行契约登记依赖和验收责任，不能由 Loop 适配器自行假定引擎已经支持。

“禁止 `setTimeout`、睡眠”应收窄为禁止宿主墙钟决定业务虚拟时间。现有 [wink_sim_js.js:43](../../../wink-micro-os/targets/wasm/wink_sim_js.js#L43) 明确区分让出事件循环与按确定数值推进虚拟时钟；宿主 watchdog、I/O 等待与取消仍需有独立墙钟期限。取消宿主 yield 本身不能证明逻辑时间正确。

**验收补强：**AT-28 增加任务唤醒与场景注入同刻、跳跃跨中间边沿、timer 与观察截止临界点、异步完成延迟及无 yield 任务的取消。既验证不重复推进，也验证没有稳定地漏掉事件。

### LS21-03 [P2] Fast Relink 应是有条件的构建优化

**位置：**计划第 95、144、226 行。

计划已有构建指纹与缓存认证，但“仅重新编译应用业务 C”的规则未附适用条件。实际 [CMakeLists.txt:138](../../../wink-micro-os/CMakeLists.txt#L138) 包含配置生成头依赖；头文件、宏、生成配置、运行时、工具链或链接参数变化均可能扩大失效集合。不能始终假定认证运行时静态库仍适用。

建议由实际构建依赖图及指纹决定重编范围；只有依赖闭包、ABI、编译/链接参数等满足复用条件时使用 Fast Relink，否则执行必要重建，必要时完整构建。避免每次无差别 clean 的性能目标合理，但不能限制正确失效处理。“单配置 60 秒”应给出实测基准、统计口径与适用范围，不得压缩合同要求的观察窗口或跳过证据。

**验收补强：**复用 AT-13，增加相同输入下增量与独立完整构建的 ABI/exports、适用业务轨迹和 verdict 一致性检查；变化触发正确失效或明确拒绝，不要求构建产物字节天然相同。

## Spec：可靠执行目标与验收完整性

### LQ21-01 [P1] Catalog 必须区分证据种类，并保留等价性未知结果

**位置：**计划第 119–124、440 行；与第 126–134 行检查分类相关。

`start` 调用置空可能属于固件依赖实验；平台注入超时/NACK 可能属于环境故障；修改业务错误分支才可能是实现变异。波特率修改在不建模线路时序的合同下还可能没有可观察影响。算子名称本身不能证明证据种类或缺陷有效性。现行 [Batch 0 证据契约第 18–21 行](../../zh/tech-designs/esp32/esp-idf-batch0-evidence-contract.md#L18) 明确区分这些检查。

每个 Catalog 条目应登记 `check_kind`、变更层/范围、适用能力及配置、触发路径、目标 claim、预期语义变化和独立见证。按实际实验及合同分类，不能用同一份实验重复填满不同必需证据槽位。

“非等价性前置证明/静态检测”还需定义可执行边界：区分可证等价、可证非等价与未知，并另列未生效/未编入/构建失败。不能仅因原有断言观察相同就判等价并过滤；那也可能是有效缺陷被弱断言漏检。未知结果进入有界调查并保留缺口，已确认有效但未检出的变异保留为存活。

**验收补强：**扩充 AT-30，验证同一算子在不同能力/合同下的分类及适用性；复用 AT-09，确保 Catalog 过滤不能消除真实的变异存活结果。

### LQ21-02 [P1] 性能约束不得妨碍有效变异的正确构建

**位置：**计划第 95、144、226 行。

该问题与 LS21-03 交叉：从需求角度，所有受控变更必须真实进入执行固件，性能不能成为复用陈旧资产或缩短必需观察的理由。补充 Fast Relink 适用前提、失效回退和增量/完整构建对照后，才能用它支撑 46 项复验的加速承诺。

### LQ21-03 [P2] “零 Flakiness”应转换为有限、可重放的验收判据

**位置：**计划第 82、108、367 行。

固定 seed 与禁用墙钟追赶尚不足以定义完成条件。需冻结重复次数、负载矩阵、事件同刻顺序、tick 量化误差、异步输入屏障及允许变化的诊断字段；在相同业务输入下比较合同定义的语义事件轨迹与 verdict，并保存可重放输入。宿主超时和资源不足仍按基础设施结果分类。

现行 [仿真生产口径第 41–47 行](../../zh/design/04-wasm-simulation/01-overview/03-production-contract.md#L41) 列有协作式 IRQ、软定时器、同刻总序反测与浮点容差等边界。确定性不自动扩大为硬实时或所有微秒行为保真承诺，观察容差仍须与实际模型能力一致。

**验收补强：**AT-28 应给出运行矩阵及比较算法，加入合同支持范围内短于 tick 的脉冲、临界期限与同刻事件；防止多次稳定通过来自固定地漏验。有限矩阵通过表达为“该验收范围内结果一致”。

### LQ21-04 [P2] Lane 配额需由冻结配置映射生成

**位置：**计划第 222、294 行。

V0-T1 强制 4 Lane 的 10/12/8/16，但未给出逐配置映射。当前 46 个 verified 配置按上游目录统计如下：

| 上游目录 | 配置数 |
|---|---:|
| get-started | 2 |
| system | 9 |
| peripherals | 16 |
| storage | 4 |
| protocols | 8 |
| wifi | 5 |
| bluetooth | 2 |
| 合计 | 46 |

若按“get-started+system / peripherals / storage / protocols+wifi+bluetooth”合并，会得到 11/16/4/15。这不是必须采用的新配额；可以按业务重新分组，但必须登记每个 `(app_id, config_id)` 的归属及理由。现有 [runner.py:102](../../../wink-micro-app/vendor/esp_idfv61/.governance/tools/loop/runner.py#L102) 还有 6 Lane 映射，新旧 lane 参数语义须有明确迁移或拒绝行为。

建议先冻结父批次精确集合，再从版本化映射派生子批次与数量。跨 Lane 聚合须核验配置键两两不交、并集等于父批次、登记及规则来源一致；切片成功不能代替父批次完整。

**验收补强：**在 AT-21/22 中明确跨 Lane 的遗漏、重叠、额外项、部分切片中断及映射版本变更，输出精确集合差异。

### LQ21-05 [P2] Inspector 的呈现效率与独立审计充分性应分别验收

**位置：**计划第 247、412、447、482 行。

计划已经要求真实独立主体与包/适用性绑定。剩余问题是“15 秒完成可信签署/一键签名”没有可靠的验收口径，且列出的基线/变异、patch、ABI 摘要不足以表达所有必需检查。

建议将 15 秒限定为约定规模下加载/定位关键证据的可用性目标。Inspector 以只读方式复用完整 verifier，呈现每个 claim/check 的覆盖、故障与恢复、来源/实际身份、回归、审计适用性、缺口和原始证据入口。签署由真实独立主体明确作出，并绑定候选包及覆盖范围；工具打开、摘要全绿或一次按键均不能自动证明审计充分。

这符合 [Batch 0 第 109 行](../../zh/tech-designs/esp32/esp-idf-batch0-evidence-contract.md#L109) 对本轮原始事实审计的要求。若提供提交审计决定的动作，也应与只读查看的副作用边界分别说明。

**验收补强：**复用 AT-26，构造基线/变异/ABI 摘要均绿，但故障、恢复、回归或审计覆盖缺项的候选；检查器必须突出缺口，正式流程不得接受其签署或晋升。
