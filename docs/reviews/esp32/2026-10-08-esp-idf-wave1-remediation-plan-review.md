## 1. 完整性判断

计划已经覆盖原评审的 S-01～S-09、Q-01～Q-06、G-01～G-03，以及上一轮复核的主要补充。没有发现遗漏整个网络领域的问题：实现正确性、生命周期、有限协议模型、配置证据、能力依赖、组合与硬件差分都有安排。

R1/R2/R3/R4 的拆分合理。后续阶段当前属于路线图，不是完整可执行规约；这已经在计划中说明，无需为了启动 R1 先写完全部协议实现。

需要优先补齐的是 R1：新增的伪代码把若干尚需契约核对的选择写成了确定实现，并删减了一些原先的失败/恢复验收。以下 M-01～M-07 应在相应工作包实施前修正或明确；M-08 为范围与诊断策略补充。它们不要求扩大到完整协议栈。

## 2. 必须修正或澄清的技术事项

### M-01 / P1：整帧接收草案仍保留截断成功，且遗漏帧元数据

**计划定位：** R1-T1，59–73 行，特别是 67–72 行。

草案仍取 `min(body_len, max_len)`，把 `pkt->len` 改为复制长度后返回 `ESP_OK`。这修复了越界补零，却没有修复容量契约。[v6.1 HTTP Server 文档](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32/api-reference/protocols/esp_http_server.html) 明确规定，整帧接收容量不足返回 `ESP_ERR_INVALID_SIZE`；分段接收是另一个 API。

草案注释说查询返回长度与类型，代码却只写 `len`。原厂 [v6.1 实现](https://raw.githubusercontent.com/espressif/esp-idf/v6.1/components/esp_http_server/src/httpd_ws.c) 从请求取 `type/final`，维护总 `len` 与剩余 `left_len`；完成的空载荷不因 payload 为空就失败。不能用调用者预填类型代替 API 输出。原厂 WS 示例目前预填 TEXT，因此可能遮蔽这种元数据缺失，不能据此说该示例已经发生回归。

**补充方案：**

- 整帧容量不足时先报错，不复制前缀、不把实际帧长改成短长度。
- 查询、整帧和分段模式分别写出 `len/type/final/left_len` 的输入输出规则；R1 维持当前文本模型的真实支持范围，类型扩展归 R2。
- 区分“空帧无待读数据”和“有待读数据但 payload 为空”，错误码以锁定版本契约为准。
- `_part` 的总帧长保持不变，剩余量和偏移随每次读取推进；不得每次查询都回绕已经消费的偏移。

**新增验收：** 12 字节帧用 8 字节整帧缓冲必须报容量错误；分段按 5/5/2 字节读取时总长一直为 12、剩余量依次为 7/2/0，拼接内容一致；零初始化 packet 查询也能得到正确的已支持类型；空帧、空指针分别覆盖。

### M-02 / P1：金丝雀测试的布局不能验证第 N+1 字节越界

**计划定位：** R1-T1，第 77 行。

“分配 `buf[16]`，末尾设置金丝雀，同时接收 16 字节并要求前 16 字节等于输入”的描述不够严谨。如果金丝雀是 `buf[15]`，它属于合法载荷区，本来就会被接收覆盖；如果直接访问 `buf[16]`，测试自身也越界。

**补充方案：** 实际分配 17 字节，向 API 声明接收容量为 16；金丝雀放在 `storage[16]`，载荷只比较 `storage[0..15]`。或使用独立 payload/guard 成员的测试结构，保证 guard 在声明容量之后。

**新增验收：** 旧实现应把 guard 改为 NUL 并使目标断言失败，修复后 guard 保持不变；载荷最后一字节选用与 guard 不同的值，避免巧合。需要时增加前置 guard，但不能以越界测试代码制造未定义行为。

### M-03 / P1：原子写预检尚缺可写容量定义，草案还改变了接口声明

**计划定位：** R1-T4，173–185 行。

`sim_bounded_stream_get_writable()` 当前不存在。新增内部辅助函数可以成立，但必须定义如何计算，不能直接用“4096 − 未读字节”。[现有流](../../../wink-micro-os/frameworks/esp_idf/src/network/sim_bounded_stream.c) 的头块只有完全读尽才释放，已经读出的头部前缀并不会自动变成可写空间。

**静态推导例：** 先写 4090 字节，再读 1 字节；四个块仍占用，尾块仅剩 6 字节。未读量为 4089，用总容量减未读量会误算为 7；随后写 7 字节仍可能先写 6 字节，再分配失败。这会重新引入计划准备消除的部分提交。

对现有“不压缩、不回收部分头块前缀”的实现，可写容量应由 **尾块未写空间 + 真正空闲块数量 × block 大小** 得到。预检与提交还需保持在相同串行/受保护上下文，不能允许另一个写者夹入后耗尽资源；不因此凭空要求给整个运行时加全局锁。

[现有头文件](../../../wink-micro-os/frameworks/esp_idf/src/network/sim_bounded_stream.h) 的参数是 `const uint8_t *data`，草案改成 `const void *data`。若保留头声明而复制函数定义，将产生不兼容声明；本批应保持原签名，新 helper 默认留在内部。

**新增验收：** 空流 4095/4096/4097；上述“写 4090→读 1→写 7”；完全释放一个头块后重新写入；失败前后原有数据、顺序、占用不变。另行明确失败可否更新背压诊断标记，避免“所有状态绝对不变”与故障计数冲突。

### M-04 / P1：HTTP open 失败不能只新增错误返回，还需回滚半初始化状态

**计划定位：** R1-T4，第 187 行。

[当前 open](../../../wink-micro-os/frameworks/esp_idf/src/network/esp_http.c) 在 376–384 行已经设置 `is_open=true`、匹配响应、声明长度及统计，并重置流，之后才写入响应。若只在第 386 行检查错误并提前 return，会留下“调用失败但内部仍已打开”的状态。

**补充方案：** 规定成功提交点和失败后的合法状态，覆盖 `is_open/is_complete`、匹配响应、请求/响应流、事件及计数。失败后应能安全 close/cleanup，并能用同一 handle 重试。区分“对端声明长度”“尝试请求”和“已经完整交付的字节”，不能简单把所有统计清零，也不能把它们全部当成功。

同时保留上一轮复核对 `perform()` 事件模式与低级读取模式的区分：事件消费者可能已从完整响应对象收到数据，不能仅因诊断缓存容量不足就无条件破坏合法事件消费。

**新增验收：** 4097 字节低级 open 失败后，无伪成功连接/完成结果；close/cleanup 安全；同 handle 再打开 512 字节响应能够成功且无旧内容。正常事件模式与低级读取模式分别回归，避免只测试流函数而漏掉客户端状态。

### M-05 / P1：HTTP stop 草案遗漏错误处理回调与上下文所有权

**计划定位：** R1-T3，139–148 行。

草案清除了 URI handlers、当前请求和 aux，但 [服务器状态](../../../wink-micro-os/frameworks/esp_idf/src/network/esp_http_server.c) 中还有 `err_handlers`。旧 404 回调仍可能在 stop/start 后被调用，不满足重新启动使用新上下文的目标。

公开 [httpd_config_t](../../../wink-micro-os/frameworks/esp_idf/include/esp_http_server.h) 108–111 行还声明全局 user/transport ctx 及其 free 回调。当前草案没有处理这些所有权，却输出所有资源已释放的日志。原厂 URI `user_ctx` 是借用指针，不能与服务器拥有的上下文一起盲目 free。

**补充方案：** R1 至少清理旧 URI/错误回调与请求状态；对已声明的全局 ctx 按契约决定释放/保留及“只释放一次”的规则。若部分会话/所有权属于 R2，明确本批关闭子集，删去超出实际行为的完成声明。

**新增验收：** 注册旧 404 回调→stop→start，旧回调不再触发；新上下文生效；适用 free 回调只执行一次，借用 ctx 不被释放；重复 stop、非法 handle 和 start 参数无效分别验证。

### M-06 / P1：方法白名单会误拒绝已经支持的 PATCH

**计划定位：** R1-T3，第 154 行。

“非 GET/POST/PUT/DELETE/HEAD 都拒绝”遗漏 PATCH。[当前实现](../../../wink-micro-os/frameworks/esp_idf/src/network/esp_http_server.c) 第 548 行已经映射 PATCH，公开枚举也包含该方法。照此执行会引入兼容性退化。

**补充方案：** 保留既有受支持方法；将未知 method token、已知方法但 URI 不允许、没有对应 URI 分别定义。明确 SDK 错误码与仿真分发器的 HTTP 状态返回约定，不能将 `ESP_ERR_NOT_SUPPORTED` 作为整数 HTTP 状态直接输出。

**新增验收：** PATCH 路由仍可执行；未知方法不触发 GET；已知但不匹配的 method 与不存在路径的结果分别符合锁定契约。R1 不要求一次实现所有新方法，但不能漏掉已有支持。

### M-07 / P1：阶段验收仍缺真实目标测试、故障恢复与受影响回归

**计划定位：** R1-T1 第 76 行、R1-T5 第 202–209 行；与 T0 第 34 行共同核对。

计划前文已正确说明 host 与 Wasm 的分工，阶段退出却只列 host/safeguards 与七个正向场景。这样仍可能没有实际验证 constructor、Wasm UART 桥接和目标特有链接路径。

所有新用例统一放到 safeguards 也需要配套说明：[该 target](../../../wink-micro-os/test/CMakeLists.txt) 当前没有 `src/network` 的 PRIVATE include 路径；`sim_uart_vprintf` 又是 static，不能凭测试名字直接调用。不能为了测试将内部目录改成 PUBLIC，或另写同样算法只测测试代码。

**建议补入阶段矩阵：**

| 工作包 | 局部验证 | 必需的集成补充 |
|---|---|---|
| T1 WS | 容量、元数据、分段规则与正确 guard | 实际 Wasm 中原厂文本路径；二进制字节边界测试不冒充完整 WS 协议交付 |
| T2 日志 | 有界格式化与 PAL 观察；static 路径的真实触达方式 | Wasm UART 实际 TX、各相关 App 的桥接安装与初始化顺序 |
| T3 HTTP | handler、错误回调、ctx 和请求隔离 | 现有注入契约下 Host 连续请求、stop/start、非法方法与恢复 |
| T4 流/客户端 | 空/非空流、读写交错与失败零提交 | HTTP client open 失败回滚/重试，以及事件与低级读取两种消费路径 |

每个目标用例应证明旧实现失败、修复后通过；测试自身 reset HTTP 状态、恢复日志 hook，避免顺序依赖。除七项正向外，按真实依赖回归现有 `test_esp_log`、`test_esp_http_client` 和受到共享日志/流改动影响的应用，不能把新增底座测试通过等同全部受影响业务通过。

新增 test target 或 PRIVATE include 属于需列出的构建修改；host、Wasm 与公开运行器的实际配置分别记录。不要求 R1 执行全部硬件验证，也不重复运行无关全量测试。

## 3. 实施时需要明确的补充

### M-08 / P2：日志修复范围与失败策略需要收敛

**计划定位：** R1-T2，第 93、100–117 行。

长度裁剪算法方向正确，但第 93 行 `n >= 512` 必然越过数组的注释仍不精确：n=512 的 512 字节读取还在数组内，只是包含 NUL；n>512 才越过数组。应区分有效文本长度与数组边界。

第 110 行继续忽略 UART 写失败。日志可以采用 best-effort 策略，但需要写明实际行为和验证方法，并覆盖空日志、负格式化返回与可控 UART 失败；不要在同一失败钩子里递归输出诊断。

第 115 行把边界修复与集中移除各 App constructor 合在一起。后者影响全局日志 hook 的初始化顺序，不能视作没有架构影响的机械去重。建议先以独立提交修好所有已知拷贝的长度，再单独实施共享桥接，明确迁移 App、初始化时机、恢复旧 hook 的规则及集成回归。若本批只做边界热修，统一桥接转入后续工作包。

## 4. 组织与交付建议

1. **修复与目标测试同一逻辑提交。** 计划 195–200 行把四个 fix 与全部测试分成最后一个 test commit，不利于单独回退和复核。建议每个 fix 带对应测试，最后一次提交只聚合阶段回归记录或必要集成测试。
2. **明确后续依赖和责任。** R2 的共享接口状态/端点/时间模型先行；TCP、HTTP/WS、SNTP 按实际依赖展开，AP 转发依赖真实数据面。R3 的身份与观察契约在模型实现前介入设计，正式晋升仍在完整验证之后。补负责人/负责角色、里程碑、前置决策和产物位置，不编造工期或把所有能力强制串行。
3. **部分关闭可追踪。** 建立问题 ID→工作包→测试→提交→复验记录的矩阵。R1 关闭 S-01/S-02 的具体缺陷及 S-06/S-08 的子集，不能顺带宣布完整 WS、全部 HTTP 生命周期或全部 S-07 大响应问题已关闭。
