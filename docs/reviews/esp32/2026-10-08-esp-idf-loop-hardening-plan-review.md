## 1. 结论与核对结果

**v1.0 的整改方向正确，但尚不足以作为“Loop 先行、防止复发”的完整执行方案。** 它覆盖了历史证据保护、严格报告核验和五类底层缺陷，却没有定义完整的候选执行边界、逐业务声明的证据要求、实际构建身份生产者、批次完成条件及交付事务。按现有条目执行完，仍可能出现局部假断言漏检、候选污染正式仓、旧产物复用或空批次成功。

建议先交付 Loop 的拒绝规则、隔离机制与对抗性回归集，再用加固后的 Loop 整改驱动和场景。对于尚缺观测能力的应用，Loop 应准确拒绝或保持候选不完整；不需要先把所有硬件模型补完，才能验证 Loop 自身的这些工程性质。

## 2. Standards：工程边界与实现可行性

### LS-01 / P1：R0 的 staging 尚不能隔离场景生成、自愈和失败重试

**计划位置：** R0-T1/T3、风险控制第 3 项（计划第 58–65、127 行）。

**源码证据：** [pipeline.py](../../../wink-micro-app/vendor/esp_idfv61/.governance/tools/loop/pipeline.py) 第 68–79 行把正式工作区交给 Agent/Remediator，第 312 行虽传入应用副本；[agent.py](../../../wink-micro-app/vendor/esp_idfv61/.governance/tools/loop/agent.py) 第 149–154 行仍在正式工作区启动进程，第 239–265 行的 Prompt 要求向正式应用路径写场景。现有 CLI 参数还可跳过自身权限确认。

**影响：** 缺场景时可能直接污染正式应用。UUID 只隔离候选文件名，不能限制 Agent、共享运行时、构建缓存或超时后仍存活的子进程。事后输入哈希检查可发现部分变化，不能阻止写入或恢复已覆盖的内容。

**补充任务：** 建立单一 `RunContext`，显式传递只读源码快照、候选应用、可写目录、构建缓存命名空间、实际配置及进程归属。修正 Prompt 的写入目标；Agent 通过受约束的候选文件/patch 接口输出，审查后才应用到隔离 checkout。cwd 或 worktree 本身不构成写权限边界。超时、取消和 failover 必须清理整棵子进程树；每次尝试采用独立目录，禁止复用失败尝试的半成品。

**验收：** 越界写入、路径穿越/链接跳转、quota 后切换 Agent、超时及取消均不改变正式 App、运行时和凭据；对实际准备执行的正常候选快照调用相同的语义/能力校验器。保留当前 `--auto-heal` 的拒绝行为，直到运行时隔离和受控补丁流程通过验收。

### LS-02 / P1：原子晋升必须覆盖完整包与全部旧写入口

**计划位置：** R0-T1 的 `promote_candidate()`（第 61 行）及 UUID 隔离承诺（第 127 行）。

**源码证据：** [evidence_verifier.py](../../../wink-micro-app/vendor/esp_idfv61/.governance/gates/evidence_verifier.py) 第 464 行先覆盖报告，第 512 行设置 verified，第 532–534 行覆写共享登记 JSON；[PowerShell 入口](../../../wink-micro-os/frameworks/esp_idf/tools/run_esp32_headless_evidence.ps1) 第 210–221 行保留 `-WriteEvidence` 入口。旧写入器还有应用模糊匹配及场景默认选择，不能只修 `config_id` fallback。

**影响：** 报告 rename 不能同时保证资产、场景、双实证包、独立审计和登记一致；两个应用并发写共享 JSON 可丢失更新。若旧入口仍接受裸报告，可绕过新晋升流程。

**补充任务：** 所有写入口复用一个正式晋升服务，要求精确 `app_id + config_id + scenario/ProofPlan` 身份及完整、经独立审计的包。先发布不可变证据包，再持共享登记锁，以预期旧版本/hash 的 CAS 检查更新唯一生效引用。报告、资产和历史审计保留原样；派生看板从登记重新生成。明确同卷 rename/replace 条件、失败恢复日志、幂等键和重启处理，不用“隔离覆盖”代替事务定义。

**验收：** 在包发布、登记切换前后注入进程终止；读者只能看到完整旧包或完整新包。两个应用并发晋升均保留更新；同配置竞争必须检测冲突；重复请求不产生不同有效结果。任何无效配置或场景在写盘前拒绝；裸报告、缺审计包及旧入口均不能直接置 verified。

### LS-03 / P1：构建和运行身份需要可靠生产者，不能只增加校验字段

**计划位置：** 全链路指纹目标、映射第 G-01/G-03 项、R0-T2（第 32、41–42、63–64 行）。

**源码证据：** [pipeline.py](../../../wink-micro-app/vendor/esp_idfv61/.governance/tools/loop/pipeline.py) 第 209 行的输入摘要只覆盖应用副本；第 339–343 行执行命令没有传递全部配置维度，第 348–350 行则把登记 backend/SoC/profile 复制进记录。目前实际设备树芯片有核对，但其他声明不能据此自动视为实际执行身份。[report_contract.py](../../../wink-micro-app/vendor/esp_idfv61/.governance/gates/report_contract.py) 第 42–51 行也明确文件 hash 和运行身份由外层绑定。

**补充任务：** 设计版本化 `build-manifest` / `run-manifest`：构建器输出实际源码及头文件依赖、配置/宏/编译参数、运行时快照、未提交变更摘要、工具链版本和构建器标识、Wasm/JS/设备树、必要插件与 ABI 契约版本。运行器/适配器输出实际命令、所用构建指纹、运行模式、backend/config/profile 映射和 run_id。collector、正式 verifier、缓存和影响分析共用这些身份定义。无法证实或实际不支持的配置明确拒绝。

**兼容约束：** 原始 Runner 报告目前没有计划要求的根 `scenario_sha256`。可先由收集器 sidecar 绑定原始输入/报告字节及运行身份；如需 Runner 新字段，应单列公开契约升级与兼容任务。SHA-256 一致性检查不等于数字签名，也不能单独证明业务因果；本轮不必引入 PKI 或 AST 规范化。

**验收：** 改共享驱动/头文件/编译参数、切换配置/backend、替换插件或借用旧缓存均使旧指纹失配；同一登记标签不能给不同实际执行贴标。运行中快照变化、发布前登记变化均阻断接受。

### LS-04 / P2：探针错误必须与合法数值区分，ABI 预检应依据观测契约

**计划位置：** 第 42、73–74、80、92–94 行。

**源码证据：** [esp_gptimer.c](../../../wink-micro-os/frameworks/esp_idf/src/drivers/esp_gptimer.c) 第 301 行的 getter 返回 `uint64_t`。返回 `0` 或 `ESP_ERR_INVALID_STATE` 都可能被消费者当作合法计数，不能称为“明确错误码”。[wink_status.h](../../../wink-micro-os/pal/include/wink_status.h) 定义具体 `WINK_ERR_*`，不是计划中的万能 `WINK_ERROR`。

**补充任务：** 先规定版本化探针的有效性/状态和值通道，以及消费端遇到无效观察时的拒绝行为；保持正常零计数合法。对逻辑目标建立“target → 观测通道/能力 → 必需 ABI”映射，检查实际链接后的 Wasm exports 和签名，而非把 `gpio:*`、`uart:*` 等 target 字符串直接对比函数名。静态断言无法证明最终链接导出。

**验收：** 无效/删除/未初始化对象触发观察无效，不能满足数值断言；合法零值可通过。缺 ABI 分类为缺失能力/契约不匹配，不能当作崩溃或变异击杀。`timer_stop` 尚不是已确认的场景动作；优先观察原厂程序自身阶段或隔离的驱动契约测试，确需新增控制动作时单列公开契约设计。

## 3. Spec：能否达成 Loop 先行与防复发目标

### LQ-01 / P1：空固件“全部通过才拦截”会漏掉局部假断言

**计划位置：** R2-T1（第 87–88 行）。

**反例：** 场景包含 GPIO 真实输出断言 A 和 ADC 夹具回读断言 B；空固件使 A 失败，B 仍通过。“全部通过才判假”不触发拦截；fail-fast 还可能让 B 根本没有被执行。整个场景依赖一处固件行为，不能推出其中所有业务声明都有效。

**补充任务：** 先通过正常基线，再按业务 `claim_id` 选择性停用对应固件输出，保持配置、夹具、观测 ABI 和运行时有效，要求指定目标断言在规定窗口产生可解释失败。每项关键声明都要有证据；重复采样断言可归属同一声明，不机械要求每个步骤重编译一次。整包空 `app_main` 只作为辅助烟雾检查，不能替代逐声明验证。

**验收：** 假真断言混合、首个真实断言 fail-fast 遮蔽后续假断言、观测缓存污染均被检出。编译失败、未知信号、缺探针、超时或无 actual 不算固件依赖证明；所有扰动后尝试恢复，并绑定实际改变的源码及固件摘要。

### LQ-02 / P1：缺少完整证据集合及有效业务变异任务

**计划位置：** R2、R4-T2 和 DoD（第 83–94、114、135 行）。

**当前边界：** [mutator.py](../../../wink-micro-app/vendor/esp_idfv61/.governance/tools/loop/mutator.py) 已明确改 matcher/激励/平台故障不能替代固件依赖或业务实现变异。通用 pipeline 当前主要改 matcher；“Canary 被击杀”只能证明断言器有效。上一轮发现的 Q-03 故障验收闭包尚无完整实施任务。

**补充任务：** 引入版本化 `ProofPlan`，按配置和业务声明登记适用检查集合：正常基线、断言器自检、环境/时序敏感性、固件依赖、有效且非等价的业务实现变异、所有已声明故障处理、恢复。每个 recipe 指定改变范围、目标声明、预期判定、有效观察/故障生效条件、时间窗口、清理方式和 hash 关系。未支持的算子或未完成证据保持候选不完整，禁止默认跳过后晋升。

**故障判定：** 故障处理用例通常应在真实故障生效后“完整通过预期降级/错误处理断言”；业务变异才应在指定断言失败。必须区分二者，不把所有非零码当成功。42 项缺少当前格式正式双实证包不等于没有历史实验；本轮应逐配置核对并补全所有已声明 negative case。

**复用点：** [report_contract.py](../../../wink-micro-app/vendor/esp_idfv61/.governance/gates/report_contract.py) 已严格校验指定 failure_index、matcher、执行前缀及计数；`verify_kill()` 已拒绝多类基础设施错误。[uart_causality.py](../../../wink-micro-app/vendor/esp_idfv61/.governance/tools/loop/uart_causality.py) 第 195–212 行有隔离源码的固件依赖/业务变异、实际 TX 和产物变化核对，第 251 行 finally 恢复；第 269 行因故障契约未证明仍保持 incomplete。应提取复用其机制，避免新增另一套宽松接受逻辑。

### LQ-03 / P1：R4 没有定义精确复验集合和批次完成语义

**计划位置：** 第 113 行 `python runner.py --limit 46`。

**源码证据：** [runner.py](../../../wink-micro-app/vendor/esp_idfv61/.governance/tools/loop/runner.py) 第 17 行使用包内相对导入，应由 `tools/run_loop.py` 启动；第 94–96 行默认跳过任一配置已 verified 的应用，第 142–144 行空集合可返回 0，第 161–164、194 行中断后也可能仅依据已处理结果返回成功。本次直接调用实际选择器，46 个 verified 配置选中数为 0。

**补充任务：** 先增加显式 reverify/冻结批次入口，以 `(app_id, config_id)` 为任务单位，从快照导出精确 46 项，保存批次身份及预期集合。`--limit` 仅是数量上限，不承担覆盖证明。记录每项结果、未执行原因、尝试次数和检查矩阵；冻结集合与最终完成集合必须相等。恢复仅复用输入/规则/环境指纹仍一致且封存完整的结果。

**验收：** 空选、漏项、重复、额外项、同应用多配置、Ctrl+C、进程崩溃和缺少必需检查均不能报告全批完成；支持恢复但不重用陈旧产物。明确候选收集完成、独立审计完成与正式交付完成三个不同边界。

### LQ-04 / P2：Q-04/Q-05 和实际候选门禁尚未落地

**计划位置：** 缺陷映射表、R4-T1、DoD（第 38–49、109–111、133–136 行）。

**遗漏：** 原评审的 LEDC 声明与允许降级不一致（Q-04）、GPIO/Deep Sleep/SoftAP 能力闭包错位（Q-05）没有任务。它们既影响验收诚实性，也影响共享驱动变化时选择哪些应用回归。只修 DAC 哈希和 SPIFFS 文件名不能修复这些结构性错误。

**补充任务：** 加入“实际 sdkconfig/源码分支 → 能力依赖 → 保真/降级合同 → 业务声明 → 验收”的一致性规则及反向影响集合测试。正常候选必须显式调用这些规则；故意改变 matcher/源码的反例按其实验契约核验，不能把整个 `runs/` 强行纳入正式交付扫描。[语义规则](../../../wink-micro-app/vendor/esp_idfv61/.governance/gates/rules/g1_scenario_semantic_integrity.py) 第 231 行排除候选是现行边界，不是候选已经通过门禁的证明。

**验收：** LEDC 要么按已允许的阶跃子集诚实命名和验收，要么实现渐变后检验时序；Deep Sleep/AP 不再错记 Light Sleep/Station；相关能力变化可选中正确回归集。DoD 列适用 Gate 2–5、分层/API lint、许可门禁、实际执行规则 ID 和禁止跳过的规则，不长期写死“12/12”。

### LQ-05 / P2：驱动整改放在通用防线之前，验收仍围绕“全部变绿”

**计划位置：** R1 先于 R2（第 68、83 行），R4 目标和 DoD（第 106–114、135 行）。

**补充任务：** 调整为 Loop 契约与对抗回归先行，再修驱动/场景，最后复验历史配置。把“100% 拦截假断言”改为有明确范围的回归承诺：本评审已知假阳性、同类变种和工程故障测试全部满足指定接受/拒绝规则；新增缺陷必须先落入持续回归集。新领域需提交观测契约、proof recipe 和已知正确/错误样本。

**验收：** Loop 既能拒绝坏候选，也能接受契约允许的正确候选，例如初始化不变量、稳态 PWM、自主闪灯及已登记降级；不能用“至少两次输入/必须变化”等固定 Prompt 规则误伤它们。复验失败应区分业务缺陷、能力缺口、观察无效、变异存活、基础设施错误、取消和证据不完整，不强迫所有配置立即变绿。

## 4. 建议的执行顺序与交付物

保留原有五类驱动整改任务，先增加下列 Loop 主线。阶段编号是对 v1.0 的修订建议，不表示这些接口已经实现。

| 阶段 | 必须交付 | 退出条件 |
|---|---|---|

## 5. 建议直接加入计划的对抗性验收集

| 维度 | 至少覆盖的测试 | 必须证明 |
|---|---|---|
| 局部假阳性 | 纯夹具回读；真实/虚假声明混合；fail-fast 遮蔽；复用上一轮观察缓存 | 假声明不能因另一条真实断言失败而逃逸 |
| 缺陷敏感性 | matcher 自检通过，但固件业务缺陷未被检出；等价/无效变异；缺失变异算子 | 自检不冒充实现缺陷证据；无效变异不充数 |
| 失败分类 | 缺 ABI、未知信号、加载失败、超时、真实故障处理、恢复失败 | 只接受指定实验的正确结果；基础设施故障不算击杀 |
| 身份与缓存 | 换应用/配置/backend/SoC/profile；改运行时或头文件；沿用旧 Wasm；运行中输入变化 | 构建与执行来源完整绑定；不可用登记标签补造实际身份 |
| 写入与恢复 | 非法参数零写入；跨目录写；子进程超时；quota/failover；晋升中途崩溃 | 正式代码/有效历史保持完整；失败尝试不污染下一次 |
| 并发与批次 | 两应用同时晋升；同配置竞争；空选；漏项；重复；取消；断点恢复 | 不丢登记更新，不混包，不把未完成批次标为成功 |
| 正确候选 | 稳态输出、初始化契约、自主时序、合法零值、已允许降级、全部声明故障正确处理 | 防线不会通过一刀切规则拒绝合法行为 |

测试优先复用现有 fixtures、`report_contract`、`verify_kill`、`twin_evidence` 和 UART 专项的机制。每个历史缺陷及后续发现的同类问题都要留下可自动执行的正反例；新增语义规则同时提供合法样本，防止门禁越改越宽或越改越死。

## 6. 需要收窄或修正的具体设计表述

- **SPI 身份：** 不能只按全局 CS 引脚路由，应包含总线/控制器与逻辑器件身份；同一 CS 编号在不同总线可以合法重复。现有 [pal_wasm_ch2_spi.c](../../../wink-micro-os/targets/wasm/pal_wasm_ch2_spi.c) 已有 `device_id` 传输契约，应先说明映射及兼容方式。计划中的 `dal_spi.c` 不是已确认现有文件；避免为模拟 EEPROM 额外扩大 DAL 职责，保持静态分发。
- **SPIFFS 范围：** 根治条件是 libc 文件访问、挂载、format、used 与复位使用同一实际 VFS 后端；“实现 RAM Flash 块设备”是一个可选方案，不能未经比选成为默认范围。先界定 mount/unmount、配额/used、格式化隔离和复位持久性合同，再决定是否需要块级模拟。
- **Target 编译：** 按文件归属制定适用矩阵：同源 App/跨平台 PAL 按双 target 验证，ESP-IDF 仿真门面按其 Host/Wasm 测试入口验证，真机使用真实 SDK。不要要求每个仿真专用 C 文件均直接编译到 xtensa；ESP32-S3 等目标还应按实际支持与编译配置明确覆盖。
- **证据措辞：** 将“Strict 双向验签”改成“版本化契约校验与摘要绑定”；将“失败正是真实缺陷”改为“失败必须按类型诊断”。Loop 应阻止缺证据晋升，同时给出准确的缺口，不能把缺能力或运行器故障误报为驱动缺陷。
- **回归出口：** 增加 `winkcli lint --pack layering --pack api`、`python .github/scripts/check_license_map.py` 及改动范围内实际需要的测试。新增的 gate/helper/schema 自身也进入 CI；规则版本变化必须影响候选和恢复结果的复用资格。

以上建议应进入计划任务与验收，而非仅补充背景说明。本次评审没有执行这些整改，也没有证明任何历史配置已完成新的全链路验收。
