# ESP-IDF 官方示例仿真治理 SOP

适用于 `wink-micro-app/vendor/esp_idfv61`。本 Skill 不替代普通固件构建、烧录流程，也不把检查请求扩大为正式交付。仓库相对命令均从 `wink-ai-embedded` 根目录执行。

## 选择任务模式与所需资料

依据用户目标选择模式；“看看、分析、审查”默认 Review。已有授权持续有效，推进阶段不自动扩大修改范围。

| 模式 | 工作与副作用 | 完成时的输出 |
|---|---|---|
| Review | 读源码、清单、契约、报告；可运行只读门禁。不构建、不仿真、不写凭据或看板。 | 当前登记状态、已核验证据、缺口及验证范围。 |
| Authoring | 在授权范围内改场景、配置；运行验证前说明实际构建与文件写入范围。不自动晋升交付状态。 | 场景与因果设计、契约预检结果、已执行及待执行检查。 |
| Reverify | 重放指定应用与验收场景；会构建及写产物、报告。使用隔离工作区保留历史证据，不带 `-WriteEvidence`。 | 本轮结果与历史结果的差异、实际配置、完整性与副作用。 |
| Delivery | 具备全部验收、审计和依赖条件后，归档当前配置凭据、复核门禁、生成看板。 | 可复核交付包、实际执行的规则、配置状态与剩余限制。 |

- 编写或审查断言时，读 [领域断言指南](references/domain-assertion-guide.md)。
- 构建、复验、故障检查或正式交付时，读 [实证工作流](references/evidence-workflow.md)，并执行其中适用的八步流程。Review 无需运行交付流程。
- 状态、范围与审计模型见 [CLASSIFICATION-SPEC.md](../../../wink-micro-app/vendor/esp_idfv61/.governance/specs/CLASSIFICATION-SPEC.md)；门面、原厂源码与回归约束见 [PLAYBOOK.md](../../../wink-micro-app/vendor/esp_idfv61/.governance/specs/PLAYBOOK.md)。
- 已发现的工具缺口与待实施修复见 [实施计划](../../../docs/implementation-plans/esp32/2026-10-01-anti-false-green-verification-plan.md)。规范要求与当前工具实现分别核验，遇到冲突报告具体缺口，不能挑选较宽松的结果宣称交付。

## 共同约束

1. 从 `wink-micro-app/vendor/esp_idfv61/.governance/data/checklist.data.json` 精确定位条目和 `executions` 数组内唯一匹配的 `config_id`。不要把配置 ID 当数组下标；不要靠模糊应用名、默认首配置、首场景补齐身份。
2. 记录目标应用、后端、芯片、profile、验收场景集合、实际构建配置、运行器版本或构建标识。指定 `config_id` 不代表运行器实际采用了它。无法确认映射时输出配置缺口，停止该配置的晋升。
3. 保持镜像的原厂业务源码及其上游哈希不变。`wink_sla.h` 是生成产物，不手工编辑。未收割 API 是能力缺口；产品排除须符合既有范围裁定与 Fail-Loud 契约，不能用空函数返回 `ESP_OK`。
4. 合法 `delivery_state` 为 `planned | building | verified | stale | regressed`。缺少运行时能力时保留适用的未交付状态，输出阻塞原因并检查依赖闭包；不写入 `blocked_on_runtime`、`unsupported` 等新交付状态，不改变产品范围来隐藏缺口。
5. 首次交付从 `planned/building` 开始；重验可读取 `verified/stale/regressed`。Review、Authoring、Reverify 不自动修改交付状态、审计或历史凭据。故障注入的预期失败不自动把正常交付标为回归失败。
6. 按 `scope.inclusion`、`audit.audited_configs` 和能力依赖闭包核验交付前置条件。使用已有有效审计；缺失时报告缺口，禁止代填 `arch_team` 或伪造签署。字段非空和门禁通过均不能证明签署真实。

## 业务验收原则

以下原则针对核心业务验收断言。辅助电源、初始化检查可保留，但不能单独代表业务成功。

| 原则 | 按业务契约判断 |
|---|---|
| A-1 因果性 | 观察值来自固件业务经过门面/协议栈产生的出口。Fixture 提供环境或对端输入，不能直接填写被断言的应用结果。 |
| A-2 行为覆盖 | 周期、时序、状态机契约检查迁移或时间窗口；初始化、稳态 PWM、不变量契约可检查稳定结果，但须有固件依赖及缺陷敏感性证据。自主闪灯无需人为外部激励。 |
| A-3 交互闭环 | 请求响应契约检查正确请求及响应处理；单向发布契约检查正确目的地、报文和业务载荷。不强加与示例目标无关的返回包。 |
| A-4 缺陷敏感性 | 事先指定有效、非等价的业务变异与对应断言；它必须在契约时限内失败。等价变异或无关变更不能用来判定假绿。 |

断言器自检、固件依赖检查、业务变异、故障处理是不同证据：改错预期仅证明断言器工作；错误密码或断网仅证明环境/故障敏感性。具体判据、隔离与恢复见实证工作流。

## 九类禁止的交付退化

| 编号 | 禁止行为 |
|---|---|
| P-1 | 非电源业务仅凭静态电源轨宣称通过；电源业务也须覆盖自身实际契约。 |
| P-2 | 恒真、过宽 Matcher 或忽略失败掩盖错误。比较字符串 `">0"` 不执行数值比较，应按契约使用正确 Matcher。 |
| P-3 | 周期/状态迁移契约仅检查初值；不能将本条套用于所有稳态或不变量测试。 |
| P-4 | 请求响应契约只验证发送，或只验证网络就绪，没有验证核心请求/响应处理。 |
| P-5 | 漏掉已声明的故障验收路径；未支持的故障探针应记录缺口，不能声称已验证健壮性。 |
| P-6 | 未实现 API、空桩、App 特化旁路直接返回成功。 |
| P-7 | 不检查冷启动或复位隔离，复用上一场景回调、任务、路由或旧报告。 |
| P-8 | 测试者或脚本伪造审计身份、范围或覆盖配置。 |
| P-9 | 无业务断言、执行集合缺失/跳过，或仅凭进程退出 0、汇总计数宣称完成。 |

## 当前工具边界

截至 2026-10-01 的本地核验结果；换版本后须重新预检。下列缺口尚未因本 Skill 修订而修复：

- `run_esp32_headless_evidence.ps1` 的 `-ConfigId/-Scenario` 只传给写入器；实际运行固定使用应用场景目录。它不提供固件禁用或自动 Canary 参数。
- 不带 `-WriteEvidence` 仍会构建、写产物与共享报告；带该开关会立即写入 `verified`。它不具备完整候选包校验、事务晋升或历史运行隔离。
- 写入器存在未知配置回退、首场景哈希、旧报告复用；`--verify-all` 尚不核对完整步骤集合、配置运行身份或因果检查结果。它通过只说明当前核验器接受已有凭据。
- `ASSERT_WAVEFORM/ASSERT_SEQUENCE` 可由当前运行时解析，但静态语义门禁尚未正确计为断言；不能增加无关点断言或绕过门禁来交差。
- 物理引脚/器件按拓扑核验；UART 总线、Wi-Fi/Netif 等逻辑观测按各自契约核验，不统一塞进 `devices`。当前 GPIO 门禁在声明为空时存在漏检，需要补充人工核查。

## Review 的只读命令

```powershell
python -X utf8 -B wink-micro-app/vendor/esp_idfv61/.governance/gates/run_gates.py --gate 1
python -X utf8 -B wink-micro-app/vendor/esp_idfv61/.governance/gates/evidence_verifier.py --verify-all
```

检查实际执行的规则及发现项：目前 Gate 1 的 12 条规则不依赖 diff 触发；Gate 2~5 按注册配置和变更范围执行，可能 SKIP。CI 的 PR 模式还须传入真实 `--changed-files`。退出 0、执行至少一条规则或 nightly 模式均不自动代表所有必需检查完成。

## Delivery 完成检查

- [ ] 应用、配置、实际后端/芯片/profile 与本轮报告身份一致；原厂源码及资产可核验。
- [ ] 声明的正常与故障验收场景均已执行；核心业务断言有逐项结果，必要步骤无缺失、重复、跳过或错误。
- [ ] 断言器自检、固件依赖、有效业务变异分别有判定记录；恢复基准通过，隔离/复位可证明。
- [ ] 运行时解析、执行与静态门禁均支持场景；物理连接和逻辑通道分别核对。
- [ ] 候选交付包绑定本轮输入、报告、场景集合与检查记录，完整性已复核；不会用共享历史文件补齐缺失证据。
- [ ] 范围、有效审计覆盖及依赖闭包满足；完成适用回归与实际必需门禁，失败时不晋升、不覆盖历史有效证据。
- [ ] 最终状态与凭据一致，写入后再核验，`CHECKLIST.md` 由生成脚本派生。

以上是交付验收要求。当前工具未自动覆盖的条目必须保留可复核的补充证据；无法证明的条目明确列为缺口。答复区分“当前登记为 verified”“当前核验器通过”“本轮完整验收完成”，并说明是否实际构建、仿真或写回。
