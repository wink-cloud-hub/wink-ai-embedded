# ESP-IDF 实证复验与交付工作流

供 `governance-sop-esp` 的 Authoring 验证、Reverify、Delivery 按需读取。以下区分验收要求和当前工具能力；不引入清单 Schema 新字段或声称未来参数已经可用。

## 1. 执行前锁定范围

- 精确定位应用 `target_app_dir` 与 `executions` 数组中的唯一 `config_id`，确认后端、芯片、profile 和验收目标。
- 用户要求单个应用时，不省略 `-App`；只运行要求的验收场景。选择完整交付时覆盖全部声明的必需场景，不能用筛选后的子集代表整个配置。
- 首次交付从 `planned/building` 开始；已有 `verified/stale/regressed` 进入复验或恢复分支。复验无需先降级登记状态。
- 固件源码、CMake/sdkconfig、资产、设备树、场景与 Fixture、运行器构建标识都是本轮输入。核对实际构建/执行设置；无法映射配置时停下晋升并报告差异。
- 构建/仿真会写文件。需要保留历史产物时使用隔离 checkout 或正确保留目录布局的工作副本；不要自动覆盖已绑定旧凭据的 `unisim-assets`。只设置 `--artifacts` 隔离报告，不能保证所有构建缓存均已隔离。

## 2. 八步流程

| 步骤 | 操作 | 核验与边界 |
|---|---|---|
| 1 锁定条目、配置与模式 | 记录精确身份、验收场景集合和状态。 | Review/Reverify 不自动写清单；首次交付、恢复交付分别记录。 |
| 2 抽取源码因果链 | 读输入、核心分支、协议处理与出口、生命周期。 | 原厂业务源码保持不变；明确哪些断言是核心业务，哪些是辅助。 |
| 3 核对依赖与门面 | 核查原子能力、真实实现、范围与有效审计覆盖。 | 缺能力不等于产品排除；Harvester 生成物不手改；复杂扩展遵守仓库计划流程。 |
| 4 场景契约预检 | 按领域指南核对 Step、Target、Matcher、时序、物理/逻辑通道。 | 解析、执行、门禁各自验证；不存在的接口或门禁误判列为缺口。 |
| 5 执行因果检验组 | 正常基准、自检、固件依赖、业务变异、故障处理、恢复。 | 各类结果不能互相替代；每轮独立启动或证明复位完整。 |
| 6 采集本轮候选证据 | 执行实际目标设置，保存正常/检查报告及输入摘要。 | 本轮身份、完整执行集合和资产可追溯；失败检查报告不交给只接受成功报告的写入器。 |
| 7 核验与晋升 | 完整性、审计、依赖和适用门禁全部通过后才纳入交付版本。 | 当前写入器并非事务接口，不能把运行成功立即写 `verified` 当作完整验收。 |
| 8 最终复核与渲染 | 对最终清单、凭据、工作区和门禁再次核验，再生成看板。 | 失败不发布该配置晋升或新看板；保留历史证据与失败诊断。 |

## 3. 因果检验组

先写明目标业务断言、预期失败方式与时限，保持原厂源码哈希不变。采用已有可核验的底层测试钩子、测试构建配置或隔离 harness；未提供相应能力时记录缺口，不捏造禁用固件或 Canary 命令。

| 检验 | 改变什么 | 保持什么 | 有效结果 |
|---|---|---|---|
| 正常基准 | 无 | 本轮标准输入、固件与正确预期 | 所有必需业务断言通过。 |
| 断言器自检 | 场景副本中一个正确预期改为明确错误预期 | 输入、固件业务、其余预期 | 指定断言实际执行并因值不符失败。只证明断言器可工作。 |
| 固件依赖 | 受控禁用固件业务执行或其关键出口路径 | 相同 Fixture、场景激励与正确预期 | 正向业务断言在时限内失败；环境仍可运行，无法用默认值或 Fixture 直填通过。 |
| 业务变异 | 指定有效非等价缺陷，如损坏 Echo TX 数据或改变核心计算 | 正常输入与原来的正确预期 | 对应业务断言失败；记录变异影响及注入点。 |
| 故障处理 | 环境或对端注入断网、超时、错误报文 | 事先声明的错误处理契约 | 应用的错误处理、恢复断言通过。不能替代固件依赖或业务变异。 |
| 恢复基准 | 解除钩子、还原副本/构建设置并冷启动 | 原来的正确输入与预期 | 正常基准重新通过，源码及输入摘要恢复。 |

解析/编译失败、未知 Target、基础设施超时、Runner 崩溃、任意非零退出均不能单独证明业务杀伤。指定输出未出现时，只有运行器完成该业务断言的观察窗口并报告其失败，才可计为杀伤。

等价变异或不触及契约的变更说明原因后排除；真实业务变异存活表示测试或业务观测存在缺口。故障检查应围绕声明的业务验收，不要求无关故障类型的固定数量。

每次检查使用独立报告。恢复放入 `try/finally` 或等效可核验清理流程；异常退出、复位失败、残留钩子或无法确认输入已恢复时，不归档成功凭据。

## 4. 当前可用的运行入口

### 4.1 不回写治理数据的整应用运行

该入口会构建、写资产与共享报告，固定运行应用场景目录。仅在授权的工作副本内使用；它不是零写入检查，也不负责完整因果检验。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File wink-micro-os/frameworks/esp_idf/tools/run_esp32_headless_evidence.ps1 -App uart_echo -Reporter json
```

当前 `-ConfigId/-Scenario` 只参与 `-WriteEvidence` 分支的归档选择，在此复验分支无选择效果。脚本无 `-Canary`、固件禁用或场景级独立报告参数。

### 4.2 单场景与独立报告

先检查 `winkcli sim run --help`。公开 CLI 当前提供 `--app`、`--mode`、`--scenarios`、`--reporter`、`--artifacts`、`--out`，未提供 `--config-id`；实际构建配置仍须另行核对。

下面是参数示例，应用目录须指向已准备好的隔离工作副本；示例的配置标记只用于本轮组织，不能充当配置已被实际采用的证明：

```powershell
$appDir = (Resolve-Path '<隔离工作区中的 uart_echo 应用绝对路径>').Path
$scenarioPath = Join-Path $appDir 'unisim-scenarios/uart_echo.scenario.json'
$runRoot = Join-Path ([System.IO.Path]::GetTempPath()) ('wink-esp-uart-echo-' + [guid]::NewGuid().ToString('N'))
$previousWinkDev = $env:WINK_DEV
try {
    $env:WINK_DEV = '1'
    winkcli sim run --app $appDir --mode headless --scenarios $scenarioPath --reporter json --artifacts (Join-Path $runRoot 'reports') --out (Join-Path $runRoot 'assets')
    if ($LASTEXITCODE -ne 0) { throw '本轮执行失败，请保留报告诊断。' }
} finally {
    $env:WINK_DEV = $previousWinkDev
}
```

若 `winkcli` 启动失败，先区分入口/环境错误与业务失败。仓库现有包装器使用同仓公开 `packages/wink-tools/wink.py` 入口，可用已配置 Python 调用相同 `sim run` 参数；不自动修改全局 Python 配置。输出文件名、逐步记录位置以本轮实际 JSON 报告为准，不能凭 CLI 退出 0 假定已经生成。

## 5. 候选报告的完整性要求

1. 预先确定场景及业务断言集合。用契约支持的场景标识及步骤索引/目标定位，不向严格场景 Schema 私自添加 `id` 字段。
2. 实际结果与预期执行集合对应，无缺失、重复、未解释的额外场景或必需步骤跳过；至少一个核心业务断言有真实逐步结果。输入步骤不能计为业务断言。
3. 正常和故障处理场景 `ok/status` 成功；逐项结果及汇总一致，`totalSteps == passedSteps > 0`，失败、错误、跳过为 0。缺失字段不能静默按 0 补齐；不同报告版本须有明确结构映射。
4. 自检、固件依赖、业务变异报告包含指定业务断言失败，其他基础设施错误不混为成功杀伤；恢复报告通过。
5. 关联实际应用、配置设置、后端、芯片/profile、资产、全部验收场景及 Fixture、运行器构建标识、每轮报告和检查类别。检查记录须指向本轮原始结果；不能靠手填“检查通过”制造证据。
6. 新运行使用唯一标识，报告与输入摘要逐轮保存，避免跨应用、配置和历史运行覆盖。报告内容摘要用于检测替换；它本身不能证明报告真实性，仍需可信执行或重放。

**现行工具限制**：写入器只绑定一个场景文件，默认取首场景；报告以应用目录下单个 `run-report.json` 覆盖保存；汇总核验未检查完整逐步执行与运行身份。不得私自改变既有 `scenario_sha256` 的单文件语义。多场景与因果检查包可保留独立原始工件供审查，但现行 `--verify-all` 不会自动核验这些补充资料，不能据其退出 0 宣称整包有效。版本化场景集合摘要与机器归档契约属于待实施计划。

## 6. 晋升与门禁

正式交付前核对范围、有效审计配置覆盖、依赖闭包、候选报告和因果证据。当前包装器的 `-WriteEvidence` 会立即晋升，不能用作自动化“采集候选”步骤。

现有写入器如用于已完整审查的候选，仅可在精确校验应用/配置/场景及本轮报告之后调用，且工作副本需可核对、可恢复：

```powershell
# 仅在 Delivery 已具备完整验收条件后执行；占位符须替换为已核验的实际值。
python -X utf8 -B wink-micro-app/vendor/esp_idfv61/.governance/gates/evidence_verifier.py --write-app '<精确条目ID>' --config-id '<已存在配置ID>' --scenario '<本轮验收场景文件>' --report-src '<本轮成功报告>' --workspace-root '<交付工作副本根目录>'
```

未知应用/配置、场景不属于验收集合、身份或报告新鲜度不明时，不调用该入口。它不拒绝所有这些错误，也没有事务保证；写入后必须核对实际修改的条目和配置，再检查最终状态。多场景完整绑定或因果证据无法证明时，停止晋升并提交工具缺口，不用首项归档替代整包。

```powershell
python -X utf8 -B wink-micro-app/vendor/esp_idfv61/.governance/gates/run_gates.py --gate 1
python -X utf8 -B wink-micro-app/vendor/esp_idfv61/.governance/gates/evidence_verifier.py --verify-all
```

现行 Gate 1 有 12 条非 diff 触发规则，核对全部实际执行及目标配置发现项。Gate 2~5 按注册规则和影响范围确定必需集合；门面修改另执行 PLAYBOOK 的 CTest、复位和分层/许可检查。`--mode nightly` 不自动取消规则的 diff 触发条件；CI PR 模式显式提供真实 `--changed-files`。`--require-executed` 仅保障数量下限，不能证明必需规则身份完整。

保留候选工作副本中修改前的清单/凭据，核验失败时不发布该晋升、保留失败结果；恢复仅限本任务改动，不能覆盖并发用户修改。全部条件通过后才把该交付变更纳入目标版本并生成看板：

```powershell
python -X utf8 -B wink-micro-app/vendor/esp_idfv61/.governance/tools/generate_checklist_v1_1.py
```

重新核对看板与最终配置，不把其他 planned 条目的警告当作本配置成功证明，也不掩盖目标配置警告。非 Delivery 模式不执行写入器和看板生成。

## 7. Skill 行为回归用例

修订规程后用只读独立验证或隔离工件检查这些决策，不能只匹配文档文字：

| 用户请求或输入 | 应产生的行为 |
|---|---|
| 只读检查已 verified 的 UART | 报告登记态和现有证据，不构建、不降级、不写清单。 |
| 复验单个 UART 配置 | 明确应用/场景、文件副作用与实际配置映射；不省略应用运行全量，不回写证据。 |
| 未实现的 HTTP 场景要交付 | 指出契约缺口，不用电源替代，不新增交付状态，不伪造审计。 |
| 波形/序列断言用于新交付 | 识别运行时解析与门禁的差异，报告阻塞，不追加无关点断言绕过。 |
| 报告 passed 但遗漏/跳过必要步骤 | 完整性失败，即便现有核验器退出 0 也不宣称整包完成。 |
| 错误配置 ID 或只有历史共享报告 | 拒绝晋升，不能默认首配置或首场景。 |
| 故障处理场景正确断言断连 | 记为故障处理通过，不计为业务变异杀伤，也不误标正常交付 regressed。 |
